## 案1：既存機能を活用し、CCが電話管理を主導

<whiteboard token="BngywmRIAhSSJYbK4LujVpc0pyb"></whiteboard>

- 既存の音声連携機能を流用し、Webhookの受信処理のみを開発
- すべての通話を **CC経由で外部へ発信し**、発信・着信の制御もCCが担います。
- AIは固定で**着信タイプ**に設定し、Daisybell側から発信することはありません。
- **着信**：CCからSIPでAIを直接呼び出して応答させます。AIが通話を終了した後、Webhookで通話記録の内容をコールバックします。
- **発信**：CCが2レッグブリッジを行います。顧客への発信と並行してSIPでDaisybell Agentを直接呼び出し（追加通話料なし）、2つの通話をブリッジします。
- **転送**：CC内の2レッグブリッジで行い、有人オペレーター（CCオペレーター）へ転送します。

## 案2：オープンAPIを一式開発し、Daisybellが電話管理を主導

<whiteboard token="QN9Cw7dirhcB74bR0Y5jPNY5pcb"></whiteboard>

- 開発が必要**オープンAPI一式**となるため、追加の開発工数が増え、期間も長くなります。
- 電話管理は **Daisybellが主導し**、CCは転送のみを担います。すべての通話は引き続きCC経由で外部へ発信します。
- AIは**着信**と**発信**の2種類に設定できます。  

  - **着信**：案1と同様に、CCからSIPでAIを直接呼び出して応答させます。
  - **発信**：APIで発信タスクを作成し、AIが発信を開始します。CCが転送して顧客へ発信します。
- **通話記録のコールバック**：通話終了後、Webhookで通話記録の内容をコールバックします（案1と同様）。
- **通話記録の照会**：オープンAPIで通話記録照会APIも提供し、通話記録の内容を能動的に取得できます。
- **転送**：案1と同様に、CC内の2レッグブリッジで行い、有人オペレーター（CCオペレーター）へ転送します。

## 案3：DaisybellがPSTNに直接接続し、CCにはデータのみ同期

<whiteboard token="YEDVwmRtSh8KcMbNx9Mj46z2pyb"></whiteboard>

- **音声経路**：Daisybell **PSTNに直接接続**し、顧客とAIをエンドツーエンドで直接接続します。着信・発信ともCCを経由しません（番号リソースは案1・2と同じ）。
- AIは**着信**と**発信**着信・発信の2種類に対応します（案2と同じ）。発信はAPIでタスクを作成し、AIが顧客へ直接発信します。
- **通話記録の同期**：音声はCCを経由せず、CC側に通話記録も作成されません。Webhook／APIで**通話記録全体をCCに同期し、通話記録を作成する必要があります**。案1・2では音声がCCを経由するため通話記録はすでに存在し、その内容を同期するだけで済みます。
- **転送**：AIからSIPでCCに直接着信し、CCがブリッジして**有人オペレーターへ転送します**（CCオペレーター）。追加通話料はかかりません。
- **電話管理**：Daisybellが全面的に主導します。有人対応への転送を除き、CCは音声経路に関与しません。
- **コストと前提条件**：番号リソースは案1・2と同じで、APIの開発規模は案2と同程度です。

## 3案の比較

音声経路、コスト、通話遅延、開発期間などの観点で比較します。

| 比較項目 | 案1：CC主導 | 案2：オープンAPI＋CC転送 | 案3：DaisybellからPSTNへ直接接続 |
|-|-|-|-|
| 音声の外部接続先 | CCに一本化（SIPでAIに直接接続） | CCに一本化し、DaisybellからCC経由で転送 | DaisybellからPSTNへ直接接続し、有人対応への転送のみCC経由 |
| 電話管理の主導者 | CCが発信・着信を制御 | Daisybellが主導し、CCは転送を担当 | Daisybellが全面的に主導し、CCはデータ同期と有人対応への転送を担当 |
| 通話経路と遅延 | 顧客 ↔ CC ↔ AI。音声はCCを1回経由（ブリッジ／転送）。案2と同じ。 | 顧客 ↔ CC ↔ AI。音声はCCを1回経由（ブリッジ／転送）。案1と同じ。 | 顧客 ↔ AIをエンドツーエンドで直接接続し、遅延を最小化（有人対応への転送はCC経由） |
| 開発コスト：CC側 | 既存の音声機能（発信・着信制御、2レッグブリッジ）を流用し、Webhook受信処理を開発 | 案1にオープンAPI連携（発信タスクの登録、通話記録の照会）を追加 | 案2に加えて、通話記録登録API（通話記録全体を受信して作成）を追加 |
| 開発コスト：Daisybell側 | 既存のAI着信機能とWebhookコールバック機能を流用でき、追加開発はほぼ不要 | オープンAPI一式（発信タスク、AI設定、通話記録API）の開発が必要で、期間は長め | オープンAPIの開発は案2と同じ。CCとのSIP連携は既存機能のため、追加期間は不要 |
| 回線・通話コスト | 通話料は全体で計算し、CC着信かDaisybell着信かで区別しません。CC ↔ AI間のSIP直結区間に追加料金はかかりません。 | 通話料は案1と同じく全体で計算します。SIP直結区間に追加料金はかかりません。 | 通話料は全体で計算します。番号リソースは案1・2と同じで、SIP直結区間に追加料金はかかりません。 |
| CCとDaisybellの結合度 | 高い：音声・制御の両方がCCを経由 | 中程度：制御はAPI、音声はCCを経由 | 低い：通話記録の同期と有人対応への転送のみCCを経由 |
| 通話記録の取得 | Webhookで通話記録の内容をコールバック（CC側に記録があるため作成不要） | Webhookのコールバック＋照会APIで通話記録の内容を同期（作成不要） | Webhook＋APIで通話記録全体を同期し、CC側で作成 |
| 拡張性・今後の発展 | CC側の機能に依存 | 通話を独自に制御できる一方、CC回線には引き続き依存 | 最も独立性が高く、単独で進化可能。有人対応への転送ではCCオペレーターを流用 |

## 通話フロー全体

### 案1：CC主導

**フローA：発信・転送 → 通話記録の保存**

1. 業務システム側からCCで発信タスクを開始
2. CCが2レッグブリッジを実行：PSTN経由で顧客へ発信し、もう一方でSIPからDaisybell Agentを直接呼び出す
3. 顧客が応答すると、CCが2つの通話をブリッジし、AIと顧客が通話
4. 有人対応へ転送する場合、CC内で2レッグブリッジを使って有人オペレーター（CCオペレーター）を呼び出し、通話を接続
5. 通話終了後、双方が切断
6. CCが通話記録を作成・保存。AIの切断後、Webhookで通話記録の内容をCCにコールバック（CC側に記録があるため作成不要）

**フローB：着信・転送 → 通話記録の保存**

1. 顧客からの着信をCCがPSTN経由で受ける
2. CCからSIPでDaisybell Agentを直接呼び出し、顧客とAIをブリッジ
3. AIと顧客が通話
4. 有人対応へ転送する場合、CC内の2レッグブリッジで有人オペレーター（CCオペレーター）を呼び出し、通話を接続
5. 通話終了後、CCが通話記録を作成・保存します。DaisybellはWebhookで内容をコールバックして補完します（作成不要）。

### 案2：オープンAPI＋CC転送

**フローA：発信・転送 → 通話記録の保存**

1. CC／業務システムがOpen API（HTTP）経由で発信タスクを作成
2. Daisybell AIが発信を開始し、音声をSIPでCCに直接送ります。CCが一元的に顧客へ発信します。
3. 顧客が応答し、AIと顧客が通話（メディアはCC経由で転送）
4. 有人対応へ転送する場合、CC内の2レッグブリッジで有人オペレーター（CCオペレーター）を呼び出し、通話を接続
5. 通話終了後、双方が切断
6. CCが通話記録を作成・保存。AIの切断後、Webhookで通話記録の内容をコールバックします（照会APIでの補完も可能。作成不要）。

**フローB：着信・転送 → 通話記録の保存**

1. 顧客からの着信をCCがPSTN経由で受け、SIPでDaisybell AIに直接転送
2. AIと顧客が通話（メディアはCC経由で転送）
3. 有人対応へ転送する場合、CC内の2レッグブリッジで有人オペレーター（CCオペレーター）を呼び出し、通話を接続
4. 通話終了後、CCが通話記録を作成・保存し、DaisybellがWebhookで内容をコールバックします（作成不要）。

### 案3：DaisybellからPSTNへ直接接続

**フローA：発信・転送 → 通話記録の保存**

1. CC／業務システムがOpen API（HTTP）経由で発信タスクを作成
2. AIがPSTN回線経由で顧客へ直接発信（CCを経由しない）
3. 顧客が応答し、AIと顧客がエンドツーエンドで直接通話
4. 有人対応へ転送する場合、AIからSIPでCCに直接着信（追加通話料なし）し、CCがブリッジして有人オペレーター（CCオペレーター）へ転送
5. 通話終了後、双方が切断
6. CC側に通話記録はありません。DaisybellがWebhook／API経由で通話記録全体をCCへ同期し、CC側で作成します。

**フローB：着信・転送 → 通話記録の保存**

1. 顧客からの着信はPSTN経由でDaisybellに直接届き、AIが応答（CCを経由しない）
2. AIと顧客がエンドツーエンドで直接通話
3. 有人対応へ転送する場合、AIからSIPでCCに直接着信し、CCがブリッジして有人オペレーター（CCオペレーター）へ接続
4. 通話終了後、Daisybellが通話記録全体をCCに同期し、CC側で作成します。
