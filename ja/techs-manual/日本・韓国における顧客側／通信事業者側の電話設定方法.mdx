本ドキュメントは、フロントチーム向けの標準リファレンスです。「電話回線をどう接続するか」「プラットフォーム側をどう設定するか」「通信事業者へどう申請するか」という疑問に明確に回答します。

本ドキュメントでは、顧客側（Daisybell プラットフォーム、顧客 PBX、電話機）、通信事業者側（日本、韓国）、および Amazon Connect、Genesys などの外部コンタクトセンタープラットフォームとの接続手順を扱います。

## ドキュメントの目的と利用方法

### 利用方法

1. シナリオを判定する：顧客保有回線との接続、自社回線からの発信、顧客 PBX との接続、または Amazon Connect／Genesys などのプラットフォーム経由の接続かを確認します。
2. 「発生したら記録する」：新しい接続方式（新しい回線種別、新しい PBX ブランド、新しいプラットフォーム、新しいパラメータの組み合わせ）が確定するたびに、該当章へ追記し、第 9 章の保守記録表にも日付と接続先を記録します。通信事業者の具体的な商務情報（料金、事業者比較、申請書類の明細）は本ドキュメントには記載せず、別途アーカイブします。
3. 第 7 章のチェックリストに従って顧客と通信事業者からパラメータを収集し、項目ごとに確認してから接続試験へ進みます。

### 保守原則

- 「発生したら記録する」：新しい接続方式（新しい通信事業者、新しい PBX ブランド、新しいプラットフォーム、新しいパラメータの組み合わせ）が確定するたびに、該当章の「対応実績」節へ追記し、日付と接続先を記録します。
- 金額、ポリシー、画面項目には有効期限があります。最新の契約書、通信事業者の現行料金表、当期のコンソールを基準にしてください。
- 顧客の電話番号、アカウントパスワード、秘密鍵に関する情報は本ドキュメントに記載せず、パラメータシートで個別に伝達します。

## 全体アーキテクチャとプラットフォーム能力の基準

### 音声経路の全体アーキテクチャ

当社システムは、自社運用の LiveKit（WebRTC メディア転送）と livekit-sip（SIP／RTP ゲートウェイ）で音声メディアを処理し、システム外へ出た後は SIP Trunk を経由して電話網（PSTN）へ接続します。

```text
Daisybell Voice Agent
        ↓
LiveKit（WebRTC メディア転送） + livekit-sip（SIP/RTP ゲートウェイ）   ← 当社プラットフォーム側
        ↓
SIP Trunk（Peer／中継経由）                              ← 接続境界
        ↓
通信事業者ネットワーク（日本／韓国）                         ← 通信事業者側
        ↓
PSTN → 顧客の携帯電話／固定電話／顧客 PBX                 ← 顧客側
```

- **顧客側**：Daisybell プラットフォーム内の回線設定、および顧客 PBX、電話機、ソフトフォンの SIP 設定。
- **通信事業者側**：電気通信回線と SIP 中継の申請、開通、接続パラメータ（サーバーアドレス、認証、コーデック、番号登録など）。
- **外部プラットフォーム側**：顧客が Amazon Connect、Genesys Cloud などのコンタクトセンタープラットフォームを利用している場合の、プラットフォーム内の設定手順。

### 2 つの接続方式：ピア（Peer）とレジスター（Register）

| 方式 | 仕組み | 適用対象 | 当社の対応状況 |
|-|-|-|-|
| ピア（Peer／IP-to-IP、Non-Register） | 双方が固定パブリック IP を使用して ACL ホワイトリストを相互設定します。定期的な登録は行わず、シグナリングを 2 つのエンドポイント間で直接伝送します。 | 通信事業者への直接接続、クラウドプラットフォーム接続、企業専用線／VPN のシナリオ | **この方式のみサポート**（P0 条件） |
| レジスター（Register） | 端末がアカウントとパスワードで通信事業者のサーバーへ定期登録し、通信事業者が登録先に応じて呼び出しをルーティングします。 | 一部の 050 サービス、固定パブリック IP がない環境、通信事業者が一般顧客に提供する標準方式 | 直接はサポートしません。中継／パートナーサービス事業者を介してピア方式へ変換する（例：中継／パートナーサービス事業者側は Register、当社側は Peer を維持）か、ピア方式に対応する事業者を選択してください。 |

<callout emoji="💡">
選定時の必須条件：Daisybell の SIP エンドポイントはピア方式（Non-Register・IP-to-IP）のみをサポートします。通信事業者またはパートナーサービス事業者に見積もりを依頼する際は、最初の P0 確認事項としてこの条件を提示してください。
</callout>

### SIP Trunk の技術要件（P0）

以下は Daisybell 開発チームが確認した技術基準です。接続する双方がいずれか 1 項目でも満たさない場合、原則として採用できません。

| 項目 | 要件 | 説明 |
|-|-|-|
| 接続方式 | Non-Register・IP-to-IP ピア | プラットフォームがサポートする唯一の方式 |
| コーデック | G.711u（PCMU） | G.722 もサポートします。接続時はネゴシエーションの曖昧さを避けるため、ulaw に限定することを推奨します。 |
| DTMF | RFC 4733 | RFC 2833 は同じ方式の旧版仕様であり、互換性を確認済みです。通信事業者が RFC 2833 を提供すれば利用できます。 |
| 方向 | 着信＋発信 | 回線ごとに同時接続数の上限を設定します。 |
| シグナリング伝送 | UDP／TCP／TLS | 通信事業者のゲートウェイ仕様に従って選択します。 |
| メディア暗号化 | None／SRTP／DTLS-SRTP | 回線のセキュリティレベルに応じて選択します。 |
| 電話番号形式 | E.164 または数字のみ | スペースと特殊文字は禁止します。 |
| 発信者番号 | 改変不可：通話ごとに指定した、通信事業者へ登録済みの番号を使用します。 | 日本の SIP 環境と同じ運用です。複数の顧客番号を登録し、通話ごとに選択できます。 |

\* Register ブリッジは計画中で、2026 年内のリリースを予定しています。

## 顧客側の設定

### Daisybell プラットフォーム側（Phone Numbers モジュール）

入口：Tools → Phone Numbers。権限：Admin と Daisybell Support は閲覧・編集できますが、Sub-user には表示されません。旧運用コンソールの［テナント管理］→［業務管理］→［回線管理］モジュールは廃止され、本モジュールが完全に引き継ぎます。ピア SIP Trunk（非登録）、DTMF RFC 4733（RFC 2833）、G.711／G.722、ネイティブ Digest 認証、TLS シグナリング暗号化、SRTP／DTLS-SRTP メディア暗号化をサポートし、着信側では送信元ホワイトリストを利用できます。

#### 発信番号（Outbound Numbers）の設定

1. Tools → Phone Numbers を開き、Outbound Numbers タブを選択して + Add New をクリックします。
2. 番号を入力します：実際に使用する発信者番号（数字のみまたは E.164）。
3. 終端ゲートウェイ（Termination URI）を指定します：通信事業者の SIP ゲートウェイのドメイン名または IP。ポートは省略できます（デフォルトは 5060）。
4. 伝送方式（UDP／TCP／TLS）とメディア暗号化（None／SRTP／DTLS-SRTP）を選択します。
5. 必要に応じて SIP 認証（Username／Password）を入力します。
6. 同時接続数の上限を設定します：発信用専用同時接続数、転送用専用同時接続数を設定し、確認後に Add Number をクリックします。

| パラメータ | 形式 | 説明 |
|-|-|-|
| Phone Number | 数字のみ／E.164 | 実際に使用する発信者番号 |
| Termination URI／Address | ドメイン:ポート または IP:ポート | 通信事業者が提供する SIP 発信ゲートウェイのアドレス（ドメインまたは IP、ポートは省略可）。例：`sip.example.com:5060` |
| Encryption | None／SRTP／DTLS-SRTP | メディアストリームの暗号化。デフォルトは None です。 |
| Transport | UDP／TCP／TLS | SIP シグナリングの伝送プロトコル。デフォルトは UDP です。 |
| SIP Authentication | Username + Password | 任意項目です。通信事業者が登録または呼び出し認証を要求する場合に入力します。保存後は平文で確認できません。 |
| Dedicated Outbound Concurrency | 整数 0～1000 | この番号で通常の発信に使用できる最大同時接続数。デフォルトは 10 です。 |
| Dedicated Transfer Concurrency | 整数 0～1000 | この番号で有人転送に使用できる最大同時接続数。デフォルトは 0 です（有人転送が必要な番号では必ず設定してください）。 |
| Show Main Caller ID For Transferred Calls | スイッチ。デフォルトはオフです。 | オンにすると、転送時も元の発信者番号を透過します。オンにする前に通信事業者が CLI 透過に対応していることを確認してください。対応していない場合、ゲートウェイに転送を拒否されることがあります。 |

#### 着信番号（Inbound Numbers）の設定

1. Inbound Numbers タブを開き、+ Add New をクリックします。
2. 着信番号（数字のみまたは E.164）を入力します。
3. セキュリティホワイトリストを設定します：SIP INVITE をプラットフォームへ送信できる送信元を指定します。形式はドメイン、IPv4、または CIDR ネットワークです。最大 20 件まで登録できます。相手の実 IP を特定できない場合は、まず 0.0.0.0/0 のワイルドカードで許可し、接続試験後に絞り込みます（下記の基準を参照）。
4. 伝送方式とメディア暗号化を選択します。
5. この番号の着信最大同時接続数を設定し、検証に合格したら Add Number をクリックします。

| パラメータ | 形式 | 説明 |
|-|-|-|
| Phone Number | 数字のみ／E.164 | 着信番号 |
| White List Address | ドメイン／IPv4／CIDR | INVITE の送信元として許可するホワイトリスト。最大 20 件で、重複した項目があると送信がブロックされます。相手の実 IP を特定できない場合は、0.0.0.0/0 のワイルドカードを入力します（下記の基準を参照）。 |
| Encryption | None／SRTP／DTLS-SRTP | メディア暗号化ポリシー |
| Transport | UDP／TCP／TLS | 着信シグナリングを受信するプロトコル |
| Total Call Concurrency | 整数 1～1000 | 同時通話接続の最大数。デフォルトは 10 です。 |

<callout emoji="💡">
**ホワイトリストの基準：**通信事業者ゲートウェイの IP／CIDR またはドメインを優先して入力します。**相手の実 IP を特定できない場合は、着信ホワイトリストに 0.0.0.0/0 のワイルドカードを設定します**（すべての送信元を許可し、接続試験を成立させます）。ワイルドカードは送信元を検証しないため、スキャンや迷惑通信のリスクがあります。接続試験が安定したら、速やかに通信事業者からゲートウェイ IP を取得し、ホワイトリストを絞り込んでください。
</callout>

#### 回線ステータスと同時接続数の境界

| ステータス | 定義 | 制限 |
|-|-|-|
| Unused（未使用） | 設定済みだが Agent にバインドされていない状態 | いつでも編集、無効化、削除できます。 |
| In Use（使用中） | 発信タスク、着信受付、または転送ポリシーに関連付けられている状態 | 削除・無効化はできません。ネットワークパラメータを変更する場合は、再確認が必要です。 |
| Disabled（無効） | 手動で無効化され、呼び出しを処理しない状態 | すべての Agent の回線一覧で非表示になります。 |

<callout emoji="💡">
同時接続数には 3 つの基準があります。発信番号の通話総同時接続数は、発信用専用同時接続数と転送用専用同時接続数の合計です。プラットフォーム画面で設定する同時接続数は、プラットフォーム側のフロー制御上限です。回線の実際の同時接続能力は、通信事業者ゲートウェイの容量で決まります。プラットフォームの上限を高く設定しても、通信事業者の回線容量を超えると通信事業者側で拒否されます（典型的には SIP 503 Service Unavailable）。
</callout>

### 顧客 PBX との接続（経路 2）

適用対象：顧客が PBX を保有し、標準 SIP に対応しており、企業専用線／VPN またはパブリックネットワークのホワイトリストによる直接接続を利用できる場合。この経路は通常、遅延とコストの面で最適です。詳細は「接続可否の判定基準」を参照してください。

#### 前提条件

- 顧客 PBX が SIP Trunk 接続（中継／peer 設定）に対応しており、メディアバイパスに対応しているかを明確にします。
- ネットワーク到達性：専用線／VPN、またはパブリックネットワーク上でホワイトリスト IP とポートを双方向に許可します。
- 顧客が PBX の外向きパブリック IP を提供できること（相互ホワイトリスト設定に使用）。
- DID のルーティングルールを確定します：どの番号を AI に着信させ、どの番号をオペレーターへ着信させ、どの番号を外線発信に使用するかを定義します。

<callout emoji="💡">
**DID 番号の割り当て元：**通信事業者経由（経路 1／経路 3）の着信では、DID は通信事業者の割り当てで決まり、回線開通時に番号リソースを申請・確認します。PBX 直結（経路 2）では、DID 番号帯を双方の協議で決定でき、通信事業者の関与は不要です。発信者番号はどちらのシナリオでも、通信事業者へ登録済みの番号を使用する必要があります。
</callout>

#### 汎用 IPPBX 中継パラメータ（FreePBX／Asterisk など）

ブランドによって項目名は異なりますが、パラメータの意味は同じです。以下では Asterisk 系で一般的な記法を例に、顧客 IT／チャネルエンジニアと認識を合わせるための基準を示します。

| パラメータ | 一般的な値 | 説明 |
|-|-|-|
| 中継タイプ | Peer（非登録）、`type=peer` | ピア方式：host に相手ゲートウェイの IP を入力します。register 文字列は不要です。 |
| サーバーアドレス／ポート | `host=<相手 IP>`。デフォルトは 5060／UDP。 | 当社と顧客がそれぞれ相手側のアドレスを設定します。ポートは接続パラメータシートに従います。 |
| ホワイトリスト ACL | `permit`／`deny` またはファイアウォールルール | 相手側 IP からの SIP／RTP トラフィックだけを許可します。 |
| コーデック | `allow=ulaw`（G.711u）を優先 | 当社の基準に合わせ、不要なトランスコードを避けます。 |
| DTMF | `dtmfmode=rfc2833` | 内線転送や IVR の二次ダイヤルはこの設定に依存します。 |
| NAT | external address／localnet | 双方のいずれかが NAT 配下にある場合は、正しく設定する必要があります。設定しない場合、片方向音声や呼び出し音が鳴らないといった症状が典型的に発生します。 |
| 着信ルーティング | DID に基づいて context をマッチング | DID を AI 回線、オペレーター、または外線発信へ振り分けます。 |
| 発信者番号 | 登録済み番号 | 発信者番号を任意に設定することはできません。第 4 章、第 5 章の通信事業者登録要件を参照してください。 |

#### 双方で交換する情報

| 方向 | 内容 |
|-|-|
| 当社 → 顧客 | SIP ゲートウェイの IP とポート、伝送プロトコル、コーデックと DTMF の要件、許可が必要な当社の送信元 IP、DID リスト、ルーティング要件 |
| 顧客 → 当社 | PBX の外向きパブリック IP、メーカーと型番、DID ルーティングルール、テスト番号とテスト時間帯、オペレーターの配置 |

### 有人転送（ブリッジ方式）

AI 通話中の有人転送はすべてブリッジ方式で行います。顧客との通話を維持したまま、オペレーターへ新しい通話を別途発信して当社側でブリッジします。有人対応中の音声は全経路で当社を通過するため、録音、文字起こし、品質検査が可能です。

| オペレーターの配置 | 設定のポイント |
|-|-|
| PBX 内線オペレーター | 経路 2 の追加設定：転送先をオペレーターの内線（顧客 PBX 経由）とする場合、転送用専用同時接続数を設定し、PBX が転送を許可していることを確認します。 |
| パブリックネットワークのカスタマーサービス番号 | 転送先を PSTN 番号とする場合：プラットフォームで転送専用番号と転送用同時接続数を設定します。通話料金は通信事業者の料金表に従います。 |
| PBX のパブリック番号から内線へ転送 | 転送先を PBX のパブリック DID＋DTMF による内線転送とする場合：顧客 IVR の内線番号と DTMF 方式（RFC 2833）を確認します。 |

<callout emoji="💡">
転送用同時接続数のデフォルトは 0 です。有人転送が必要な番号では、発信／着信設定で Dedicated Transfer Concurrency を必ず設定してください。設定しないと転送を開始できません。
</callout>

## 通信事業者側（日本）

### 番号と回線種別

| 種別 | 番号形式 | 特徴と適用対象 |
|-|-|-|
| 0AB-J 固定番号 | 03／06／0X-XXXX-XXXX | 市外局番付きの固定電話です。企業の識別性が高く、発信者番号の信頼度も最も高い一方、開通には回線資格が必要で、通信事業者または代理店経由での申請が必要です。 |
| 050 IP 電話 | 050-XXXX-XXXX | IP 電話番号で、低コストかつ短期間で開通できます。AI 発信やカスタマーサービスに適しています。一部の信頼性が重視される用途では、050 は 0AB-J より認知度が低くなります。 |
| 携帯電話番号 | 090／080／070-XXXX-XXXX | 通常は業務用の発信者番号には使用しません。利用する場合は、事前に通信事業者へ実現可否とコンプライアンスを確認してください。 |

### 一般的な接続方式

#### SIP Trunk のピア接続（主流）

- 双方が固定パブリック IP を使用し、ACL ホワイトリストを相互設定します。
- コーデックは PCMU に限定し、DTMF には RFC 2833／4733 を使用します。
- 発信者番号には「指定した登録済み番号」方式を使用します。顧客の番号を証明書類に基づいて登録し、発信時に SIP メッセージで登録済み番号から選択します。
- 同時接続数、CPS（1 秒あたりの発信数）の制限、SLA を確認します。

#### 050 IP 電話サービス

市場にある 050 サービスの多くは登録型（アカウントとパスワードによる登録）です。選定時には、まずピア接続に対応しているか（P0）を確認してください。Register 方式しか提供しないサービスは、ゲートウェイ／中継を介して Peer へ変換するか、ピア方式に対応するサービス事業者へ切り替える必要があります。

### 申請・開通の手順と必要書類

1. 要件を確認します：番号種別（0AB-J／050）、同時接続数、着信と発信の比率、月間通話量、発信者番号の要件。
2. 申込を提出します：会社情報、代表者、事業者情報（番号）、申請番号、チャネル数。多くのサービスでは資格審査が必要です。
3. 開通：期間はサービス事業者によって数日から数週間です。途中で審査結果と開通時期を確認します。
4. 通信事業者の開通資料（SIP パラメータと番号情報）を取得し、第 4.2 節に従ってホワイトリストとパラメータを相互設定します。
5. 通話試験：着信、発信、DTMF、発信者番号、同時接続数を項目ごとに検証してから本番運用へ移行します。

| 開通後に通信事業者から取得する情報 | 内容 |
|-|-|
| ゲートウェイ情報 | SBC／SIP サーバーのアドレスとポート、伝送プロトコル（UDP／TCP／TLS） |
| メディアパラメータ | コーデック、DTMF 方式、メディア暗号化の要否 |
| 認証方式 | IP ピア＋ACL、またはアカウントとパスワード |
| 番号情報 | 割り当て番号の一覧、発信者番号の登録要件と形式（国内形式／E.164）、登録可能数、必要書類 |
| 容量と保証 | 同時接続数の上限、CPS 制限、SLA、営業電話に関するポリシー |
| テスト支援 | テスト番号、テスト時間帯、接続試験の担当者 |

### 日本での注意事項

- 発信者番号の登録制：なりすまし対策の規制対象であり、発信者番号には通信事業者へ登録済みの番号を使用する必要があります。任意の番号は設定できません。
- コンプライアンス：個人情報の取り扱いは個人情報保護法（APPI）に従います。録音時は告知が必要です。通話データとログは合意した範囲で保存し、適切にマスキングします。
- 緊急通報：0AB-J 系の回線では設置場所の登録が必要です（110／119 の位置情報）。移転時には更新してください。

## 通信事業者側（韓国）

### 番号体系

| 種別 | 説明 |
|-|-|
| 070 인터넷전화 | インターネット電話番号で、韓国の AI／コンタクトセンター業務で主流の選択肢です。 |
| 지역번호（地域番号） | 02（ソウル）、031／032／051／053 など。企業の識別性が高く、番号ポータビリティ（번호이동）により既存番号を維持できます。 |
| 대표번호（代表番号） | 15XX／16XX／18XX の企業代表番号で、コンタクトセンター用途に紐づけられます。 |
| 대안번호（代替番号） | 050 系の企業番号で、個人携帯番号の発信者番号表示に代えて使用します。 |

### 接続経路

韓国の通信事業者は、第三者 AI ベンダーとの直接 SIP 接続に対して一般に慎重で、個別審査となることが多いです。実際に利用可能な経路は次の 2 種類です。

- 通信事業者へ直接接続するピア回線サービス（IP-to-IP Peer、Non-Register）。
- 通信事業者ネットワークの中継／パートナーサービス事業者を経由して接続します。当社側は Peer（Non-Register）を維持し、通信事業者側はパートナーサービス事業者が Register 方式で接続します。プラットフォームのエンドポイントから見れば、ピア方式の技術条件を満たします。

### 韓国での注意事項

- 緊急通報（긴급통신）の設置場所申告は法的義務です。設置場所を変更する場合は申告が必要で、119／112 の位置情報に影響します。
- 発信者番号の登録制：顧客が保有する 02／070 番号は、加入証明または契約証明を提出して発信者番号として登録できます。迷惑電話や発信者番号の改ざんを行うと、回線停止または契約解除となる場合があります（韓国共通の規制）。
- 番号ポータビリティ（번호이동）：顧客の既存番号を維持できます。実現可否、費用、期間は回線提供事業者へ個別に確認してください。
- 通話ごとに登録済み発信者番号を指定します。日本と同じ運用で、同一環境に複数顧客の番号を登録し、SIP メッセージで通話ごとに選択できます。

## 外部コンタクトセンタープラットフォームとの接続（Amazon Connect／Genesys）

顧客がクラウドコンタクトセンタープラットフォームを利用している場合、接続作業の重点は通信事業者から外部システムであるプラットフォーム内の設定へ移ります。代表的な方式は 2 つです。Amazon Connect は Flow＋Lambda による動的 DTMF 転送、Genesys Cloud は外部 SIP Trunk（BYOC）接続を使用します。

### Amazon Connect（Lambda による動的 DTMF 転送）

シナリオ：着信が Amazon Connect の音声 Contact Flow に入った後、Lambda を呼び出して着信発信者番号を読み取り、DTMF シーケンスを生成します。続いて Transfer to phone number ブロックが呼び出しを対象番号（AI 回線や下流 IVR など）へ転送し、下流側が DTMF で顧客番号を識別します。

```text
着信 → Amazon Connect Flow → Invoke Lambda（CustomerEndpoint.Address を読み取り
     → 番号をクレンジング → DtmfSequence を返却）
   → Set contact attributes（External → User defined）
   → Transfer to phone number（動的に DTMF を送信）→ 対象番号
```

#### プラットフォーム側の設定手順（AWS コンソール）

1. Lambda コンソールで関数を作成します（Connect インスタンスと関数は同じアカウント・リージョン。例は東京の ap-northeast-1）。番号クレンジングコードをデプロイし、`Details.ContactData.CustomerEndpoint.Address` を読み取り、数字以外の文字を除去して `DtmfSequence` を返します（取り決め例：先頭のコンマで一時停止し、元の番号に + がある場合は `*`、末尾に `#` を付けます。`+ → *` は下流 IVR の取り決めです。接続試験で確認してください）。
2. Connect コンソール → 対象インスタンス → Flows → AWS Lambda functions で、この関数を追加します。同一アカウント・同一リージョンの場合、Lambda のリソースポリシーが自動生成されます（Principal は connect.amazonaws.com）。
3. Flow を構築します：Set logging behavior（テスト期間は Enable）→ AWS Lambda function ブロック（Invoke Lambda／Synchronous／JSON 検証、Timeout はまず 3000 ms）→ Set contact attributes（External.DtmfSequence を User defined.DtmfSequence にコピーし、キー名の大文字・小文字を一致させる）→ Transfer to phone number（対象 DID は E.164、Caller ID を設定し、Send DTMF では動的属性を参照）。
4. Success／Error／Timeout の各分岐を個別に接続し、保存して Publish します。着信番号が公開済みフローに関連付けられていることを確認します。

#### 主な制限とトラブルシューティング

| 項目 | 説明 |
|-|-|
| DTMF の長さ | Transfer to phone number で送信できる DTMF 文字は最大 50 文字です。コンマ 1 つにつき 750 ミリ秒の一時停止が入ります。 |
| 同期呼び出しのタイムアウト | Lambda の同期呼び出しは最長 8 秒です。Timeout はまず 3000 ms に設定し、CloudWatch の実行時間に応じて調整します。 |
| 403 AccessDeniedException | Lambda のリソースポリシーを確認します。connect.amazonaws.com に lambda:InvokeFunction が許可されているか、SourceArn／SourceAccount が想定したインスタンスを指しているか、関数が正しいインスタンスとリージョンに追加されているかを確認してください。 |
| Lambda の実行記録がない | Connect のリージョン、Flow 内の関数 ARN、CloudWatch のリージョンと時間範囲を確認します。 |
| 属性が空 | 返却キーが DtmfSequence になっているか、External → User defined のマッピングが正しいかを確認します。 |
| 転送は成功したが DTMF を受信できない | まず固定の短いシーケンス（例：123#）で経路を検証し、次に動的属性の参照を確認します。Connect のログだけでは下流側が実際にキー入力を受信したことを証明できないため、対象側で確認してください。 |

検証順序の推奨：静的転送（固定 DID、Lambda は呼び出さない）→ 固定 DTMF → 動的マッピング → 番号のエンドツーエンド。一度に 1 つの変数だけを変更します。Lambda コード、権限ポリシーの詳細、CloudWatch Flow Logs の利用方法、リリース前チェックリストを含む完全な手順書は添付ファイルを参照してください。

### Genesys Cloud（外部 SIP Trunk 接続）

Genesys 側では外部 SIP Trunk 接続を使用します。顧客が保有する通信事業者回線を BYOC（Bring Your Own Carrier）クラウドトランク経由で Genesys Cloud に接続し、Genesys と通信事業者／当社の間は標準 SIP で接続します。

#### 前提条件

- Genesys Cloud のライセンスと BYOC の有効化（BYOC は Genesys へ申請して開通します）。
- 接続する双方が固定パブリック IP を使用し、ホワイトリストを相互設定して SIP／RTP ポートを許可すること。
- 回線のメディアパラメータがプラットフォーム基準と一致すること：G.711、RFC 2833／4733、UDP／TCP／TLS。

#### 設定手順

1. Genesys Cloud の管理センターで External Trunk（BYOC）を作成し、通信事業者または接続先の SBC アドレス、ポート、プロトコルを入力します。
2. シグナリングとメディアのパラメータ（コーデック、DTMF、伝送、暗号化）を設定し、第 2.3 節のプラットフォーム基準に合わせます。
3. ホワイトリスト／ACL を双方向に設定し、ネットワーク到達性を確認します。
4. 番号ルーティングを設定します：DNIS を対応する Architect フローまたは転送先にマッチングします。
5. 接続試験を行います：着信、発信、DTMF、発信者番号、同時接続数を項目ごとに確認してから本番運用へ移行します。

## よくある問題のクイックトラブルシューティング

| 現象 | 優先確認項目 |
|-|-|
| 着信 403 Forbidden | 着信ホワイトリストが通信事業者の SBC／ゲートウェイ IP または CIDR ネットワークを完全にカバーしているか |
| 発信 503 Service Unavailable | 同時接続数の上限が通信事業者の回線容量を超えていないか。回線の利用時間帯制限も確認します。 |
| 通信事業者が Register 方式しか提供しない | 当社プラットフォームは Register をサポートしません。中継／パートナーサービス事業者を介して Peer へ変換するか、ピア方式に対応する事業者を選択してください。 |
| 片方向音声／音声なし | NAT と RTP アドレスの設定（external address、STUN、ファイアウォールで RTP ポート範囲を許可）を確認し、SRTP 設定が双方で一致しているか確認します。 |
| 発信者番号が正しくない、または拒否される | 発信者番号が通信事業者へ登録済みか、転送時の透過スイッチと通信事業者の CLI 透過対応を確認します。 |
| IVR メニューに入れない／内線転送に失敗する | DTMF 方式が RFC 2833／4733 か、転送 DTMF の 50 文字上限とシーケンス形式（+ → \* の取り決め）を確認します。 |
| まったく発信できない | 伝送プロトコルとポート、ファイアウォール、番号形式（E.164）、通信事業者の開通状態を確認します。 |
| Agent の回線ドロップダウンに番号が表示されない | 回線が Disabled になっていないか、着信番号と Agent の呼び出しモード（Inbound）が一致しているかを確認します。 |
| 未使用のテスト番号を削除できない | いずれかの Agent で予備転送番号として設定されていないか確認します（依存関係がある場合は In Use です）。 |
