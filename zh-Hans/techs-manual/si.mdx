## 方案一：基于现有能力，CC 主导电话管理

<whiteboard token="LIMWwDSCyh0XFJbxGuWjEwhCppP"></whiteboard>

- 复用现有语音对接能力，仅需开发 Webhook 接收
- 所有电话统一经 **CC 对外**，外呼与接听控制均由 CC 主导
- AI 固定配置为**接听类型**，Daisybell 侧不主动发起呼叫
- **呼入**：CC 经直接 SIP 呼叫 AI 接听，AI 挂断后通过 Webhook 回调话单内容
- **外呼**：CC 双呼桥接 —— 一边外呼客户，一边经直接 SIP 呼叫 Daisybell Agent（无额外话费），桥接两路通话
- **转接**：在 CC 内基于双呼桥接完成，转接给人工客服（CC 坐席）

## 方案二：开发完整开放接口，Daisybell 主导电话管理

<whiteboard token="YSmBw1AfyhY4cbbmkevjTpR3pbf"></whiteboard>

- 需开发**完整的开放接口**，额外开发工作量更大、周期更长
- 电话管理由 **Daisybell 主导**，CC 仅充当转发；所有电话仍统一经 CC 对外
- AI 支持配置为**接听**和**外呼**两种类型：  

  - **接听**：同方案一，CC 经直接 SIP 呼叫 AI 接听
  - **外呼**：经 API 创建外呼任务，由 AI 发起，经 CC 转发外呼客户
- **话单回调**：挂断后通过 Webhook 回调话单内容（同方案一）
- **话单查询**：开放接口另提供话单查询 API，可主动查询话单内容
- **转接**：同方案一，在 CC 内基于双呼桥接完成，转接给人工客服（CC 坐席）

## 方案三：Daisybell 直连 PSTN，仅数据同步 CC

<whiteboard token="Xdsbw6qxPhkvbMbogPxjvlQ1pge"></whiteboard>

- **语音链路**：Daisybell **直接接入 PSTN**，客户与 AI 端到端直连，呼入 / 外呼不经过 CC（号码资源与方案一 / 二相同）
- AI 支持配置为**接听**和**外呼**两种类型（同方案二）：外呼经 API 创建任务，由 AI 直接外呼客户
- **话单同步**：语音不过 CC、CC 侧无话单，需经 Webhook / API 将**完整话单同步至 CC 并创建话单**；方案一 / 二语音经 CC 已有话单，仅需同步话单内容
- **转接**：AI 经直接 SIP 呼入 CC，由 CC 桥接**转接给人工客服**（CC 坐席），无额外话费
- **电话管理**：完全由 Daisybell 主导；除转接人工外，CC 不参与语音链路
- **成本与前提**：号码资源与方案一 / 二相同，接口开发量与方案二相当

## 三种方案对比

从语音链路、成本、通话延迟、开发周期等维度对比如下：

| 维度 | 方案一 · CC 主导 | 方案二 · 开放接口 + CC 转发 | 方案三 · Daisybell 直连 PSTN |
|-|-|-|-|
| 语音对外出口 | CC 统一对外（直接 SIP 对接 AI） | CC 统一对外，Daisybell 经 CC 转发 | Daisybell 直连 PSTN，仅转接人工经 CC |
| 电话管理主导 | CC 主导外呼与接听控制 | Daisybell 主导，CC 充当转发 | Daisybell 完全主导，CC 承担数据同步与转接人工 |
| 通话链路与延迟 | 客户 ↔ CC ↔ AI，语音经 CC 一跳（桥接 / 转发），与方案二相同 | 客户 ↔ CC ↔ AI，语音经 CC 一跳（桥接 / 转发），与方案一相同 | 客户 ↔ AI 端到端直连，延迟最低（转接人工经 CC） |
| 开发成本 · CC 侧 | 复用现有语音能力（外呼 / 接听控制、双呼桥接），需开发 Webhook 接收 | 在方案一基础上，增加开放 API 对接（外呼任务下发、话单查询） | 在方案二基础上，额外增加话单录入接口（接收完整话单并创建话单） |
| 开发成本 · Daisybell 侧 | 复用现有 AI 接听与 Webhook 回调能力，几乎无额外开发 | 需开发完整开放接口（外呼任务、AI 配置、话单 API），周期较长 | 开放接口开发同方案二；与 CC 的 SIP 对接为现有能力，无需额外周期 |
| 线路与通话成本 | 电话费整体计算，不区分接 CC 还是 Daisybell；CC ↔ AI 直接 SIP 段无额外话费 | 电话费整体计算，同方案一；直接 SIP 段无额外话费 | 电话费整体计算，号码资源与方案一 / 二相同；直接 SIP 段无额外话费 |
| CC 与 Daisybell 耦合度 | 紧耦合，语音与控制均经 CC | 中耦合，控制走 API、语音经 CC | 松耦合，仅话单同步与转接人工经 CC |
| 话单获取 | Webhook 回调话单内容（CC 已有话单，无需创建） | Webhook 回调 + 查询 API 同步话单内容（无需创建） | Webhook + API 同步完整话单，由 CC 创建话单 |
| 扩展与演进 | 依赖 CC 侧能力 | 可自主调度话务，仍依赖 CC 线路 | 最自主、可独立演进；转接人工复用 CC 坐席 |

## 完整话务流程

### 方案一 · CC 主导

**流程 A：外呼 + 转接 → 话单保存**

1. 业务侧在 CC 发起外呼任务
2. CC 双呼桥接：一路经 PSTN 外呼客户，一路经直接 SIP 呼叫 Daisybell Agent
3. 客户应答，CC 桥接两路，AI 与客户通话
4. 需转人工时，CC 在内基于双呼桥接呼叫人工客服（CC 坐席）并接续
5. 通话结束、双方挂机
6. CC 生成并保存话单；AI 挂断后经 Webhook 将话单内容回调至 CC（CC 已有话单，无需创建）

**流程 B：接听 + 转接 → 话单保存**

1. 客户来电，CC 经 PSTN 接听
2. CC 经直接 SIP 呼叫 Daisybell Agent，桥接客户与 AI
3. AI 与客户通话
4. 需转人工时，CC 在内双呼桥接呼叫人工客服（CC 坐席）并接续
5. 通话结束后 CC 生成并保存话单，Daisybell 经 Webhook 回调话单内容补充（无需创建）

### 方案二 · 开放接口 + CC 转发

**流程 A：外呼 + 转接 → 话单保存**

1. CC / 业务系统经 Open API（HTTP）创建外呼任务
2. Daisybell AI 发起外呼，语音经直接 SIP 送至 CC，由 CC 统一对外拨打客户
3. 客户应答，AI 与客户通话（媒体经 CC 转发）
4. 需转人工时，CC 在内双呼桥接呼叫人工客服（CC 坐席）并接续
5. 通话结束、双方挂机
6. CC 生成并保存话单；AI 挂断后经 Webhook 回调话单内容（亦可经查询 API 补充，无需创建）

**流程 B：接听 + 转接 → 话单保存**

1. 客户来电，CC 经 PSTN 接听，经直接 SIP 转接至 Daisybell AI
2. AI 与客户通话（媒体经 CC 转发）
3. 需转人工时，CC 在内双呼桥接呼叫人工客服（CC 坐席）并接续
4. 通话结束后 CC 生成并保存话单，Daisybell 经 Webhook 回调话单内容（无需创建）

### 方案三 · Daisybell 直连 PSTN

**流程 A：外呼 + 转接 → 话单保存**

1. CC / 业务系统经 Open API（HTTP）创建外呼任务
2. AI 经 PSTN 线路直接外呼客户（不经 CC）
3. 客户应答，AI 与客户端到端直连通话
4. 需转人工时，AI 经直接 SIP 呼入 CC（无额外话费），CC 桥接转接给人工客服（CC 坐席）
5. 通话结束、双方挂机
6. CC 侧无话单：Daisybell 经 Webhook / API 将完整话单同步至 CC，由 CC 创建话单

**流程 B：接听 + 转接 → 话单保存**

1. 客户来电经 PSTN 直达 Daisybell，AI 接听（不经 CC）
2. AI 与客户端到端直连通话
3. 需转人工时，AI 经直接 SIP 呼入 CC，CC 桥接人工客服（CC 坐席）
4. 通话结束后，Daisybell 将完整话单同步至 CC 并由 CC 创建话单
