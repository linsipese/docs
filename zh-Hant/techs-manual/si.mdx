## 方案一：基於現有能力，CC 主導電話管理

<whiteboard token="TJRXw8KMqhRAwYbCr3FjWR4npVc"></whiteboard>

- 複用現有語音對接能力，僅需開發 Webhook 接收
- 所有電話統一經 **CC 對外**，外撥與接聽控制均由 CC 主導
- AI 固定設定為**接聽類型**，Daisybell 側不主動發起呼叫
- **呼入**：CC 經直接 SIP 呼叫 AI 接聽，AI 掛斷後通過 Webhook 回調通話記錄內容
- **外撥**：CC 雙呼橋接 —— 一邊外撥客戶，一邊經直接 SIP 呼叫 Daisybell Agent（無額外話費），橋接兩路通話
- **轉接**：在 CC 內基於雙呼橋接完成，轉接給人工客服（CC 坐席）

## 方案二：開發完整開放介面，Daisybell 主導電話管理

<whiteboard token="MnQAwddrDhPnF4bZPOWj31qEpNI"></whiteboard>

- 需開發**完整的開放介面**，額外開發工作量更大、週期更長
- 電話管理由 **Daisybell 主導**，CC 僅充當轉發；所有電話仍統一經 CC 對外
- AI 支持設定為**接聽**和**外撥**兩種類型：  

  - **接聽**：同方案一，CC 經直接 SIP 呼叫 AI 接聽
  - **外撥**：經 API 建立外撥任務，由 AI 發起，經 CC 轉發外撥客戶
- **通話記錄回調**：掛斷後通過 Webhook 回調通話記錄內容（同方案一）
- **通話記錄查詢**：開放介面另提供通話記錄查詢 API，可主動查詢通話記錄內容
- **轉接**：同方案一，在 CC 內基於雙呼橋接完成，轉接給人工客服（CC 坐席）

## 方案三：Daisybell 直連 PSTN，僅資料同步 CC

<whiteboard token="S7tcwfRnyhBZnXb7LRkjOszapYd"></whiteboard>

- **語音鏈路**：Daisybell **直接接入 PSTN**，客戶與 AI 端到端直連，呼入 / 外撥不經過 CC（號碼資源與方案一 / 二相同）
- AI 支持設定為**接聽**和**外撥**兩種類型（同方案二）：外撥經 API 建立任務，由 AI 直接外撥客戶
- **通話記錄同步**：語音不過 CC、CC 側無通話記錄，需經 Webhook / API 將**完整通話記錄同步至 CC 並建立通話記錄**；方案一 / 二語音經 CC 已有通話記錄，僅需同步通話記錄內容
- **轉接**：AI 經直接 SIP 呼入 CC，由 CC 橋接**轉接給人工客服**（CC 坐席），無額外話費
- **電話管理**：完全由 Daisybell 主導；除轉接人工外，CC 不參與語音鏈路
- **成本與前提**：號碼資源與方案一 / 二相同，介面開發量與方案二相當

## 三種方案對比

從語音鏈路、成本、通話延遲、開發週期等維度對比如下：

| 維度 | 方案一 · CC 主導 | 方案二 · 開放介面 + CC 轉發 | 方案三 · Daisybell 直連 PSTN |
|-|-|-|-|
| 語音對外出口 | CC 統一對外（直接 SIP 對接 AI） | CC 統一對外，Daisybell 經 CC 轉發 | Daisybell 直連 PSTN，僅轉接人工經 CC |
| 電話管理主導 | CC 主導外撥與接聽控制 | Daisybell 主導，CC 充當轉發 | Daisybell 完全主導，CC 承擔資料同步與轉接人工 |
| 通話鏈路與延遲 | 客戶 ↔ CC ↔ AI，語音經 CC 一跳（橋接 / 轉發），與方案二相同 | 客戶 ↔ CC ↔ AI，語音經 CC 一跳（橋接 / 轉發），與方案一相同 | 客戶 ↔ AI 端到端直連，延遲最低（轉接人工經 CC） |
| 開發成本 · CC 側 | 複用現有語音能力（外撥 / 接聽控制、雙呼橋接），需開發 Webhook 接收 | 在方案一基礎上，增加開放 API 對接（外撥任務下發、通話記錄查詢） | 在方案二基礎上，額外增加通話記錄錄入介面（接收完整通話記錄並建立通話記錄） |
| 開發成本 · Daisybell 側 | 複用現有 AI 接聽與 Webhook 回調能力，幾乎無額外開發 | 需開發完整開放介面（外撥任務、AI 設定、通話記錄 API），週期較長 | 開放介面開發同方案二；與 CC 的 SIP 對接為現有能力，無需額外週期 |
| 線路與通話成本 | 電話費整體計算，不區分接 CC 還是 Daisybell；CC ↔ AI 直接 SIP 段無額外話費 | 電話費整體計算，同方案一；直接 SIP 段無額外話費 | 電話費整體計算，號碼資源與方案一 / 二相同；直接 SIP 段無額外話費 |
| CC 與 Daisybell 耦合度 | 緊耦合，語音與控制均經 CC | 中耦合，控制走 API、語音經 CC | 松耦合，僅通話記錄同步與轉接人工經 CC |
| 通話記錄取得 | Webhook 回調通話記錄內容（CC 已有通話記錄，無需建立） | Webhook 回調 + 查詢 API 同步通話記錄內容（無需建立） | Webhook + API 同步完整通話記錄，由 CC 建立通話記錄 |
| 擴展與演進 | 依賴 CC 側能力 | 可自主調度話務，仍依賴 CC 線路 | 最自主、可獨立演進；轉接人工複用 CC 坐席 |

## 完整話務流程

### 方案一 · CC 主導

**流程 A：外撥 + 轉接 → 通話記錄儲存**

1. 業務側在 CC 發起外撥任務
2. CC 雙呼橋接：一路經 PSTN 外撥客戶，一路經直接 SIP 呼叫 Daisybell Agent
3. 客戶應答，CC 橋接兩路，AI 與客戶通話
4. 需轉人工時，CC 在內基於雙呼橋接呼叫人工客服（CC 坐席）並接續
5. 通話結束、雙方掛機
6. CC 生成並儲存通話記錄；AI 掛斷後經 Webhook 將通話記錄內容回調至 CC（CC 已有通話記錄，無需建立）

**流程 B：接聽 + 轉接 → 通話記錄儲存**

1. 客戶來電，CC 經 PSTN 接聽
2. CC 經直接 SIP 呼叫 Daisybell Agent，橋接客戶與 AI
3. AI 與客戶通話
4. 需轉人工時，CC 在內雙呼橋接呼叫人工客服（CC 坐席）並接續
5. 通話結束後 CC 生成並儲存通話記錄，Daisybell 經 Webhook 回調通話記錄內容補充（無需建立）

### 方案二 · 開放介面 + CC 轉發

**流程 A：外撥 + 轉接 → 通話記錄儲存**

1. CC / 業務系統經 Open API（HTTP）建立外撥任務
2. Daisybell AI 發起外撥，語音經直接 SIP 送至 CC，由 CC 統一對外撥打客戶
3. 客戶應答，AI 與客戶通話（媒體經 CC 轉發）
4. 需轉人工時，CC 在內雙呼橋接呼叫人工客服（CC 坐席）並接續
5. 通話結束、雙方掛機
6. CC 生成並儲存通話記錄；AI 掛斷後經 Webhook 回調通話記錄內容（亦可經查詢 API 補充，無需建立）

**流程 B：接聽 + 轉接 → 通話記錄儲存**

1. 客戶來電，CC 經 PSTN 接聽，經直接 SIP 轉接至 Daisybell AI
2. AI 與客戶通話（媒體經 CC 轉發）
3. 需轉人工時，CC 在內雙呼橋接呼叫人工客服（CC 坐席）並接續
4. 通話結束後 CC 生成並儲存通話記錄，Daisybell 經 Webhook 回調通話記錄內容（無需建立）

### 方案三 · Daisybell 直連 PSTN

**流程 A：外撥 + 轉接 → 通話記錄儲存**

1. CC / 業務系統經 Open API（HTTP）建立外撥任務
2. AI 經 PSTN 線路直接外撥客戶（不經 CC）
3. 客戶應答，AI 與客戶端到端直連通話
4. 需轉人工時，AI 經直接 SIP 呼入 CC（無額外話費），CC 橋接轉接給人工客服（CC 坐席）
5. 通話結束、雙方掛機
6. CC 側無通話記錄：Daisybell 經 Webhook / API 將完整通話記錄同步至 CC，由 CC 建立通話記錄

**流程 B：接聽 + 轉接 → 通話記錄儲存**

1. 客戶來電經 PSTN 直達 Daisybell，AI 接聽（不經 CC）
2. AI 與客戶端到端直連通話
3. 需轉人工時，AI 經直接 SIP 呼入 CC，CC 橋接人工客服（CC 坐席）
4. 通話結束後，Daisybell 將完整通話記錄同步至 CC 並由 CC 建立通話記錄
