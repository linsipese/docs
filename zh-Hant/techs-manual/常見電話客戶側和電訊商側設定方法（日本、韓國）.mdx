本文件是前場團隊的標準參考手冊：對「電話線路怎麼接」「平臺側怎麼配」「電訊商怎麼申請」這些問題作出了明確解答。

本文件覆蓋客戶側（Daisybell 平臺、客戶 PBX 與話機）、電訊商側（日本、韓國）以及 Amazon Connect、Genesys 等外部呼叫平臺的對接流程。

## 文件用途與使用方法

### 使用方法

1. 判斷場景：客戶自帶線路對接、我方線路外撥、客戶 PBX 對接，還是經 Amazon Connect / Genesys 等平臺對接。
2. 「遇到即記錄」：每次新的對接方式（新線路類型、新 PBX 品牌、新平臺、新參數組合）確定後，追加到對應章節並在第 9 章維護記錄表登記，註明日期與對接方。具體電訊商商務資訊（報價、廠商對比、申請材料明細）不寫入本文件，另行歸檔。
3. 按第 7 章清單向客戶與電訊商收集參數，逐項覈對後進入聯調。

### 維護原則

- 「遇到即記錄」：每次新的對接方式（新電訊商、新 PBX 品牌、新平臺、新參數組合）確定後，追加到對應章節的「已接觸記錄」小節，並註明日期與對接方。
- 金額、政策、界面欄位有時效性，以最新合同、電訊商牌價和當期控制檯爲準。
- 涉及客戶號碼、賬號密碼、密鑰的資訊不寫入本文件，參數單單獨傳遞。

## 總體架構與平臺能力基線

### 語音鏈路總體架構

我方系統通過自部署的 LiveKit（WebRTC 媒體轉發）與 livekit-sip（SIP/RTP 網關）承載語音媒體，出系統後經 SIP Trunk 落地到電話網（PSTN）。

```text
Daisybell Voice Agent
        ↓
LiveKit（WebRTC 媒體轉發） + livekit-sip（SIP/RTP 網關）   ← 我方平臺側
        ↓
SIP Trunk（對等 / 經中繼）                              ← 對接邊界
        ↓
電訊商網絡（日本 / 韓國）                                ← 電訊商側
        ↓
PSTN → 客戶手機 / 固話 / 客戶 PBX                        ← 客戶側
```

- **客戶側**：Daisybell 平臺內的線路設定，以及客戶 PBX、話機、軟終端上的 SIP 設定。
- **電訊商側**：電信線路與 SIP 中繼的申請、開通與對接參數（服務器地址、鑑權、編解碼、號碼登記等）。
- **外部平臺側**：客戶已在使用 Amazon Connect、Genesys Cloud 等呼叫平臺時，平臺內的設定流程。

### 兩種對接模式：對等（Peer）與註冊（Register）

| 模式 | 原理 | 適用 | 我方支持情況 |
|-|-|-|-|
| 對等（Peer / IP-to-IP，Non-Register） | 雙方使用靜態公網 IP 互配 ACL 白名單，不做週期註冊，信令直接在兩個端點間傳遞 | 電訊商直連、雲平臺對接、企業專線 / VPN 場景 | **僅支持此模式**（P0 條件） |
| 註冊（Register） | 終端用賬號密碼向電訊商服務器週期註冊，電訊商按註冊位置路由呼叫 | 部分 050 服務、無固定公網 IP 的環境、電訊商對一般客戶的預設方式 | 不直接支持；需經中繼 / 合作服務商轉換爲對等（如經中繼 / 合作服務商轉換：我方段保持對等，電訊商段註冊），或選擇支持對等的供應商 |

<callout emoji="💡">
選型硬條件：Daisybell SIP 端點僅支持對等方式（Non-Register · IP-to-IP）。向電訊商或合作服務商詢價時，把這一條作爲 P0 問題第一個確認。
</callout>

### SIP Trunk 技術要求（P0）

以下爲 Daisybell 開發團隊確認的技術基線，對接雙方任一項不滿足原則上不可採用：

| 項目 | 要求 | 說明 |
|-|-|-|
| 對接模式 | Non-Register · IP-to-IP 對等 | 平臺唯一支持方式 |
| 編解碼 | G.711u（PCMU） | 另支持 G.722；對接時建議限定 ulaw 避免協商歧義 |
| DTMF | RFC 4733 | RFC 2833 爲同一方式的舊版規範，已確認兼容；電訊商以 RFC 2833 提供即可 |
| 方向 | 呼入 + 呼出 | 按線路分別設定併發配額 |
| 信令傳輸 | UDP / TCP / TLS | 按電訊商網關規範選擇 |
| 媒體加密 | None / SRTP / DTLS-SRTP | 按線路安全等級選擇 |
| 號碼格式 | E.164 或純數字 | 禁止空格與特殊字符 |
| 外撥主叫 | 非篡改：按通話指定電訊商已登記號碼 | 與日本 SIP 環境做法一致；支持登記多家客戶號碼並按通話選擇 |

\* Register橋接器已在計劃中，預計2026年內可以上線

## 客戶側設定

### Daisybell 平臺側（Phone Numbers 模塊）

入口：Tools → Phone Numbers。權限：Admin 與 Daisybell Support 可查看和編輯，Sub-user 不可見。原營運後臺【租戶管理】→【業務管理】→【線路管理】模塊已下線，由本模塊完全接管。支持對等 SIP Trunk（非註冊）、DTMF RFC 4733（RFC 2833）、G.711 / G.722，原生 Digest 摘要認證、TLS 信令加密與 SRTP / DTLS-SRTP 媒體加密，呼入側支持來源白名單。

#### 呼出號碼（Outbound Numbers）設定

1. 進入 Tools → Phone Numbers，選中 Outbound Numbers 頁籤，點擊 + Add New。
2. 填寫號碼：真實呼出主叫號碼（純數字或 E.164）。
3. 指定終止網關（Termination URI）：電訊商 SIP 網關的域名或 IP，端口可省略（預設 5060）。
4. 選擇傳輸方式（UDP / TCP / TLS）與媒體加密（None / SRTP / DTLS-SRTP）。
5. 按需填寫 SIP 認證（Username / Password）。
6. 設定併發配額：專用外撥併發、專用轉接併發，確認後點擊 Add Number。

| 參數 | 格式 | 說明 |
|-|-|-|
| Phone Number | 純數字 / E.164 | 真實呼出主叫號碼 |
| Termination URI / Address | 域名:端口 或 IP:端口 | 電訊商提供的 SIP 呼出網關地址（域名或 IP，端口可省略），如 `sip.example.com:5060` |
| Encryption | None / SRTP / DTLS-SRTP | 媒體流加密，預設 None |
| Transport | UDP / TCP / TLS | SIP 信令傳輸協議，預設 UDP |
| SIP Authentication | Username + Password | 可選；電訊商要求註冊 / 呼叫認證時填寫，保存後不可查看明文 |
| Dedicated Outbound Concurrency | 整數 0–1000 | 該號碼常規外撥最大併發，預設 10 |
| Dedicated Transfer Concurrency | 整數 0–1000 | 該號碼人工轉接最大併發，預設 0（需要轉人工的號碼務必設定） |
| Show Main Caller ID For Transferred Calls | 開關，預設關閉 | 開啓後轉接時仍透傳初始主叫；開啓前必須確認電訊商支持 CLI 透傳，否則轉接可能被網關拒絕 |

#### 呼入號碼（Inbound Numbers）設定

1. 進入 Inbound Numbers 頁籤，點擊 + Add New。
2. 填寫呼入號碼（純數字或 E.164）。
3. 設定安全白名單：允許向平臺推送 SIP INVITE 的來源，格式爲域名、IPv4 或 CIDR 網段，最多 20 條；無法確定對方實際 IP 時先填 0.0.0.0/0 通配放行（聯調後收緊，見下方口徑說明）。
4. 選擇傳輸方式與媒體加密。
5. 設定該號碼的最大呼入併發，校驗通過後點擊 Add Number。

| 參數 | 格式 | 說明 |
|-|-|-|
| Phone Number | 純數字 / E.164 | 呼入號碼 |
| White List Address | 域名 / IPv4 / CIDR | 允許推送 INVITE 的來源白名單，最多 20 條，重複條目阻斷提交；無法確定對方實際 IP 時填 0.0.0.0/0 通配（見下方口徑說明） |
| Encryption | None / SRTP / DTLS-SRTP | 媒體加密策略 |
| Transport | UDP / TCP / TLS | 接收呼入信令的協議 |
| Total Call Concurrency | 整數 1–1000 | 最大同時通話連接數，預設 10 |

<callout emoji="💡">
**白名單口徑：**優先填寫電訊商網關 IP / CIDR 或域名；**無法確定對方實際 IP 時，入站白名單設定爲 0.0.0.0/0 通配**（放行全部來源，保障聯調接通）。通配等於不校驗來源，存在被掃描騷擾的風險，聯調穩定後應儘快向電訊商索取網關 IP 並收緊白名單。
</callout>

#### 線路狀態與併發邊界

| 狀態 | 定義 | 限制 |
|-|-|-|
| Unused（未使用） | 已設定但未綁定 Agent | 可隨時編輯、停用、刪除 |
| In Use（使用中） | 已關聯外撥任務、呼入接待或轉接策略 | 不能刪除與停用；修改網絡參數需二次確認 |
| Disabled（已禁用） | 人爲停用，不處理呼叫 | 在所有 Agent 線路列表中隱藏 |

<callout emoji="💡">
併發有三個口徑：呼出號碼的通話總併發等於外撥專用併發加轉接專用併發；平臺界面設定的併發是平臺側流控配額；線路實際併發能力由電訊商網關容量決定。平臺配額配得再高，超出電訊商通道容量時呼叫仍會在電訊商側被拒（典型爲 SIP 503 Service Unavailable）。
</callout>

### 客戶 PBX 對接（鏈路二）

適用：客戶有 PBX 且支持標準 SIP，可開通企業專線 / VPN 或公網白名單直連。此路徑時延與成本通常最優，詳見「可對接性判斷標準」。

#### 前置條件

- 客戶 PBX 支持 SIP Trunk 接入（提供中繼 / peer 設定能力），並明確是否支持媒體旁路。
- 網絡可達：專線 / VPN，或公網雙向放行白名單 IP 與端口。
- 客戶可提供 PBX 出口公網 IP（用於互配白名單）。
- 確定 DID 路由規則：哪些號碼進 AI、哪些進坐席、哪些出局。

<callout emoji="💡">
**DID 號碼來源：**經電訊商落地（鏈路一 / 鏈路三）的呼入，DID 由電訊商分配決定，在線路開通時申請確認號碼資源；PBX 直連（鏈路二）場景下，DID 號碼段由雙方協商確定即可，無需電訊商參與。呼出外顯號碼在兩種場景下均須使用電訊商已登記號碼。
</callout>

#### 通用 IPPBX 中繼參數（FreePBX / Asterisk 等）

各品牌欄位名不同，參數含義一致。以下以 Asterisk 系常見寫法爲例，供與客戶 IT / 渠道工程師溝通時對齊口徑：

| 參數 | 常見取值 | 說明 |
|-|-|-|
| 中繼類型 | Peer（不註冊），`type=peer` | 對等模式：host 填對方網關 IP；不需要 register 字符串 |
| 服務器地址 / 端口 | `host=<對方IP>`，預設 5060/UDP | 我方與客戶各配對方的地址；端口按對接參數單 |
| 白名單 ACL | `permit`/`deny` 或防火牆規則 | 僅允許對端 IP 的 SIP / RTP 流量 |
| 編解碼 | `allow=ulaw`（G.711u）優先 | 與我方基線一致，避免不必要轉碼 |
| DTMF | `dtmfmode=rfc2833` | 轉分機、IVR 二次撥號依賴此項 |
| NAT | external address / localnet | 兩側任一處於 NAT 後必須正確設定，否則典型症狀爲單向語音或無法振鈴 |
| 呼入路由 | 按 DID 匹配 context | DID 分流到 AI 線路、坐席或出局 |
| 外顯號碼 | 已登記號碼 | 不可任意設定主叫，見第 4、5 章電訊商登記要求 |

#### 雙方互換資訊

| 方向 | 內容 |
|-|-|
| 我方 → 客戶 | SIP 網關 IP 與端口、傳輸協議、編解碼與 DTMF 要求、需放行的我方出口 IP、DID 清單與路由要求 |
| 客戶 → 我方 | PBX 出口公網 IP、廠商與型號、DID 路由規則、測試號碼與測試窗口、坐席位置 |

### 轉接人工（橋接模式）

AI 通話中轉接人工統一採用橋接模式：保持與客戶的通話不變，另向坐席發起一路新呼叫並在我方橋接，人工階段音頻全程經我方，可錄音、轉寫與質檢。

| 坐席位置 | 設定要點 |
|-|-|
| PBX 內線坐席 | 鏈路二疊加：轉接目標爲坐席分機（經客戶 PBX），需設定專用轉接併發，並確認 PBX 對轉接放行 |
| 公網客服號碼 | 轉接目標爲 PSTN 號碼：在平臺設定專用轉接號碼與轉接併發；通話費按電訊商牌價 |
| PBX 公網號碼轉分機 | 轉接目標爲 PBX 公網 DID + DTMF 轉分機：確認客戶 IVR 的分機號與 DTMF 方式（RFC 2833） |

<callout emoji="💡">
轉接併發預設爲 0。凡是有轉人工需求的號碼，必須在呼出 / 呼入設定中設定 Dedicated Transfer Concurrency，否則轉接無法發起。
</callout>

## 電訊商側（日本）

### 號碼與線路類型

| 類型 | 號碼格式 | 特點與適用 |
|-|-|-|
| 0AB-J 固定號碼 | 03 / 06 / 0X-XXXX-XXXX | 市外局番固定電話，企業識別度高、外顯可信度最高；開通需線路資質或經電訊商 / 代理申請 |
| 050 IP 電話 | 050-XXXX-XXXX | IP 電話號碼，成本低、開通快，適合 AI 外撥與客服場景；部分受信場景對 050 的認可度低於 0AB-J |
| 手機號碼 | 090 / 080 / 070-XXXX-XXXX | 一般不作爲業務外顯；選用前與電訊商確認可行性與合規 |

### 常見接入方式

#### SIP Trunk 對等接入（主流）

- 雙方靜態公網 IP，互配 ACL 白名單。
- 編解碼限定 PCMU，DTMF 用 RFC 2833 / 4733。
- 外撥主叫採用「指定已登記號碼」方式：客戶號碼經證明後登記，外撥時在 SIP 報文中從已登記號碼中選擇。
- 確認併發、CPS（每秒呼叫數）限制與 SLA。

#### 050 IP 電話服務

市面上 050 服務多爲註冊型（賬號密碼註冊）。選型時先確認是否支持對等接入（P0）：僅提供註冊模式的服務，需經網關 / 中繼轉換爲對等，或改選支持對等的服務商。

### 申請開通流程與材料

1. 確認需求：號碼類型（0AB-J / 050）、併發路數、呼入呼出比例、月話務量、外顯要求。
2. 提交申込：公司資訊、代表者、事業者資訊（番號）、申請號碼與信道數；多數服務需要資質審查。
3. 開通：週期按服務商數日至數週不等；中途確認審查結果與開通時間。
4. 取得電訊商開通資料（SIP 參數與號碼資訊），按第 4.2 節互配白名單與參數。
5. 呼叫測試：呼入、呼出、DTMF、外顯、併發逐項驗證後上線。

| 開通後向電訊商索取 | 內容 |
|-|-|
| 網關資訊 | SBC / SIP 服務器地址與端口、傳輸協議（UDP / TCP / TLS） |
| 媒體參數 | 編解碼、DTMF 方式、是否要求媒體加密 |
| 鑑權方式 | IP 對等 + ACL，或賬號密碼 |
| 號碼資訊 | 分配號碼清單、主叫登記要求與格式（國內格式 / E.164）、可登記數量與所需材料 |
| 容量與保障 | 併發上限、CPS 限制、SLA、營銷電話政策 |
| 測試支持 | 測試號碼、測試窗口、聯調聯繫人 |

### 日本注意事項

- 主叫號碼登記制：受防僞冒監管約束，外撥主叫須爲電訊商已登記號碼，不能任意設定。
- 合規：個人資訊處理遵循《個人資訊保護法》（APPI）；錄音需告知；通話數據與日誌按約定範圍留存與脫敏。
- 緊急通報：0AB-J 類線路須登記安裝地址（110 / 119 定位），遷移時更新。

## 電訊商側（韓國）

### 號碼體系

| 類型 | 說明 |
|-|-|
| 070 인터넷전화 | 網絡電話號碼，韓國 AI / 呼叫中心業務的主流選擇 |
| 지역번호（地域號碼） | 02（首爾）、031 / 032 / 051 / 053 等；企業識別度高，可經攜號轉網（번호이동）保留原有號碼 |
| 대표번호（代表號碼） | 15XX / 16XX / 18XX 企業代表號，綁定呼叫中心場景 |
| 대안번호（替代號碼） | 050 系企業號碼，替代個人手機號外顯 |

### 接入路徑

韓國電訊商對第三方 AI 廠商的直接 SIP 對接通常較爲審慎、個案審批。實際可行路徑有兩類：

- 直連電訊商的對等線路產品（IP-to-IP Peer，Non-Register）。
- 經電訊商網絡的中繼 / 合作服務商接入：我方段保持對等（Non-Register），電訊商段由合作服務商以註冊方式對接，從平臺端點看仍滿足對等技術條件。

### 韓國注意事項

- 緊急通報（긴급통신）地址申報是法定義務：安裝地址變更必須申報，影響 119 / 112 定位。
- 主叫號碼登記制：客戶原有 02 / 070 號碼可憑入網證明或合同證明後登記爲外撥主叫；垃圾電話與篡改主叫會被停機或解約（韓國通用監管）。
- 攜號轉網（번호이동）：可保留客戶原有號碼，可行性與費用、週期需向線路提供方個案確認。
- 按通話指定已登記主叫：與日本做法一致，支持多家客戶號碼登記於同一環境、按通話在 SIP 報文中選用。

## 外部呼叫平臺對接（Amazon Connect / Genesys）

客戶已在使用雲呼叫中心平臺時，對接工作重點從電訊商轉向平臺內（外部系統）的設定流程。兩類典型方式：Amazon Connect 走 Flow + Lambda 動態 DTMF 轉接；Genesys Cloud 走外部 SIP Trunk（BYOC）連接。

### Amazon Connect（Lambda 動態 DTMF 轉接）

場景：來電進入 Amazon Connect 語音 Contact Flow 後，呼叫 Lambda 讀取來電主叫號碼並生成 DTMF 序列，再由 Transfer to phone number 塊將呼叫轉接到目標號碼（如 AI 線路 / 下游 IVR），下游按 DTMF 識別客戶號碼。

```text
來電 → Amazon Connect Flow → Invoke Lambda（讀取 CustomerEndpoint.Address
     → 清洗號碼 → 返回 DtmfSequence）
   → Set contact attributes（External → User defined）
   → Transfer to phone number（動態發送 DTMF）→ 目標號碼
```

#### 平臺側設定步驟（AWS 控制檯）

1. Lambda 控制檯建立函數（Connect 實例與函數同賬號同區域，示例 ap-northeast-1 東京），部署號碼清洗代碼：讀取 `Details.ContactData.CustomerEndpoint.Address`，去除非數字字符，返回 `DtmfSequence`（約定示例：首位逗號暫停、原號碼帶 + 時轉爲 `*`、末尾 `#`；`+ → *` 是下游 IVR 約定，聯調時確認）。
2. Connect 控制檯 → 目標實例 → Flows → AWS Lambda functions，添加該函數；同賬號同區域會自動生成 Lambda 資源策略（Principal 爲 connect.amazonaws.com）。
3. 搭建 Flow：Set logging behavior（測試期 Enable）→ AWS Lambda function 塊（Invoke Lambda / Synchronous / JSON 校驗，Timeout 先 3000 ms）→ Set contact attributes（External.DtmfSequence 複製到 User defined.DtmfSequence，鍵名大小寫一致）→ Transfer to phone number（目標 DID 用 E.164、設定 Caller ID、Send DTMF 引用動態屬性）。
4. 分別連接 Success / Error / Timeout 分支，保存並 Publish，確認入站號碼關聯已發佈流程。

#### 關鍵限制與排障

| 項 | 說明 |
|-|-|
| DTMF 長度 | Transfer to phone number 最多發送 50 個 DTMF 字符；每個逗號暫停 750 毫秒 |
| 同步呼叫超時 | Lambda 同步呼叫最長 8 秒；Timeout 先設 3000 ms，按 CloudWatch 執行時長調整 |
| 403 AccessDeniedException | 檢查 Lambda 資源策略：是否允許 connect.amazonaws.com 的 lambda:InvokeFunction，SourceArn / SourceAccount 是否指向預期實例；函數是否已添加到正確實例與區域 |
| Lambda 無執行記錄 | 覈對 Connect 區域與 Flow 中函數 ARN、CloudWatch 區域與時間範圍 |
| 屬性爲空 | 返回鍵是否爲 DtmfSequence；External → User defined 映射是否正確 |
| 轉接成功但未收到 DTMF | 先用固定短序列（如 123#）驗證通道，再查動態屬性引用；Connect 日誌無法證明下游實際收到按鍵，需在目標端確認 |

驗證順序建議：靜態轉接（固定 DID，不調 Lambda）→ 固定 DTMF → 動態映射 → 號碼端到端，一次只改一個變量。完整手冊（含 Lambda 代碼、權限策略細節、CloudWatch Flow Logs 用法與上線檢查表）見附件：

### Genesys Cloud（外部 SIP Trunk 連接）

Genesys 側使用外部 SIP Trunk 連接：客戶自帶電訊商線路經 BYOC（Bring Your Own Carrier）雲中繼接入 Genesys 雲，Genesys 與電訊商 / 我方之間按標準 SIP 對接。

#### 前置條件

- Genesys Cloud 許可與 BYOC 授權（BYOC 需向 Genesys 申請開通）。
- 對接雙方靜態公網 IP，互配白名單，放行 SIP / RTP 端口。
- 線路媒體參數與平臺基線一致：G.711、RFC 2833 / 4733、UDP / TCP / TLS。

#### 設定流程

1. 在 Genesys Cloud 管理中心建立 External Trunk（BYOC），錄入電訊商 / 對接側的 SBC 地址、端口與協議。
2. 設定信令與媒體參數（編解碼、DTMF、傳輸與加密），與第 2.3 節平臺基線對齊。
3. 雙向設定白名單 / ACL，確認網絡可達。
4. 設定號碼路由：DNIS 匹配到對應的 Architect 流程或轉接目標。
5. 聯調驗證：呼入、呼出、DTMF、外顯、併發逐項確認後上線。

## 對接資訊收集清單

| 收集對象 | 資訊項 |
|-|-|
| 客戶電話系統 | 有無 PBX / 呼叫中心平臺；廠商與型號；是否支持標準 SIP（Trunk 接入與 SIP 分機）；是否支持媒體旁路；PBX 出口公網 IP |
| 號碼資源 | 外顯號碼歸屬（我方申請或客戶提供）；日本區分 0AB-J 與 050，韓國區分 02 / 070；號碼登記材料（入網 / 合同證明）；DID 號碼：經電訊商落地由電訊商分配，PBX 直連由雙方協商確定 |
| 網絡條件 | 專線 / VPN / 公網白名單；防火牆與 NAT 策略；可放行的 IP 與端口 |
| 媒體參數 | 編解碼（G.711 等）、是否需要轉碼、DTMF 方式、媒體加密要求 |
| 話務模型 | 併發路數、外撥與呼入比例、轉人工比例、每日話務量（分鐘數） |
| 坐席側 | 人工坐席位置（PBX 分機 / 公網號碼 / 客戶呼叫中心），決定轉接路徑與轉接併發配額 |
| 電訊商側（申請後） | 接入模式（對等 / 註冊，對等爲 P0）；SBC 地址與端口；傳輸 / 編解碼 / DTMF；鑑權方式；主叫登記要求與可登記數量；併發與 CPS；SLA；開通週期；測試號碼與窗口 |
| 我方平臺側 | P0 條件覈對（第 2.3 節）；號碼是否已在 Phone Numbers 登記；外撥併發 / 轉接併發配額；呼入白名單；號碼格式 E.164 |

## 常見問題排查速查

| 現象 | 優先檢查 |
|-|-|
| 呼入 403 Forbidden | 呼入白名單是否完整覆蓋電訊商 SBC / 網關 IP 或 CIDR 網段 |
| 呼出 503 Service Unavailable | 併發配額是否超過電訊商通道容量；線路時間窗限制 |
| 電訊商只提供註冊模式 | 我方平臺不支持註冊：經中繼 / 合作服務商轉換或改選支持對等的供應商 |
| 單向語音 / 無音頻 | NAT 與 RTP 地址設定（external address、STUN、防火牆放行 RTP 端口段）；SRTP 設定是否兩端一致 |
| 外顯號碼不對或被拒 | 主叫是否已在電訊商登記；轉接透傳開關與電訊商 CLI 透傳支持 |
| IVR 菜單無法進入 / 轉分機失敗 | DTMF 方式是否 RFC 2833 / 4733；轉接 DTMF 50 字符上限與序列格式（+ → \* 約定） |
| 完全呼不通 | 傳輸協議與端口、防火牆、號碼格式（E.164）、電訊商開通狀態 |
| Agent 線路下拉不顯示號碼 | 線路是否 Disabled；呼入號碼與 Agent 呼叫模式（Inbound）是否匹配 |
| 閒置測試號碼無法刪除 | 是否被任何 Agent 設定爲備用轉接號碼（存在依賴即爲 In Use） |
