This is the frontline team's standard reference for connecting telephone lines, configuring the platform, and applying for carrier services.

It covers customer-side configuration (the Daisybell platform, customer PBXs, and phones), carrier-side configuration in Japan and Korea, and integrations with external calling platforms such as Amazon Connect and Genesys.

## 2. Overall Architecture and Platform Baseline

### 2.1 Overall Voice Path

Our system carries voice media using self-hosted LiveKit (WebRTC media relay) and livekit-sip (SIP/RTP gateway). Calls leave our system through a SIP Trunk and connect to the public telephone network (PSTN).

```text
Daisybell Voice Agent
        ↓
LiveKit (WebRTC media relay) + livekit-sip (SIP/RTP gateway)   ← Our platform
        ↓
SIP Trunk (peer or through a relay)                             ← Integration boundary
        ↓
Carrier network (Japan or Korea)                                ← Carrier side
        ↓
PSTN → Customer mobile phone / landline / customer PBX           ← Customer side
```

- **Customer side**: Configure lines in Daisybell and SIP settings on the customer's PBX, desk phones, and softphones.
- **Carrier side**: Apply for and provision telephone service and SIP trunks, including server addresses, authentication, codecs, and number registration.
- **External platform side**: Configure an existing customer calling platform, such as Amazon Connect or Genesys Cloud.

### 2.2 Two Integration Modes: Peer and Register

| Mode | How it works | Typical use | Support in our platform |
|-|-|-|-|
| Peer (IP-to-IP, Non-Register) | Both parties use static public IP addresses and configure reciprocal ACL allowlists. There is no periodic registration; signaling passes directly between the two endpoints. | Only supported mode |  **(P0 requirement)**This is the only supported mode and is a P0 requirement. |
| Register | An endpoint periodically registers with the carrier's server using a username and password. The carrier routes calls based on the registration location. | Some 050 services, environments without a static public IP address, and the default setup offered to ordinary carrier customers. | Not directly supported. Use a relay or partner to convert the carrier-facing Register segment to a Peer connection on our side, or choose a provider that supports Peer. |

<callout emoji="💡">
Hard requirement for provider selection: Daisybell SIP endpoints support only Peer (Non-Register, IP-to-IP). Make this the first P0 question when requesting a quote from a carrier or integration partner.
</callout>

### 2.3 SIP Trunk Technical Requirements (P0)

The following baseline was confirmed by the Daisybell development team. If either party cannot meet any item, the connection is generally unsuitable.

| Item | Requirement | Notes |
|-|-|-|
| Integration mode | Non-Register, IP-to-IP Peer | The only mode supported by the platform. |
| Codec | G.711u (PCMU) | G.722 is also supported. For integration, limiting negotiation to ulaw is recommended to avoid ambiguity. |
| DTMF | RFC 4733 | RFC 2833 is the older specification for the same method and has been confirmed as compatible; a carrier that offers RFC 2833 is acceptable. |
| Call direction | Inbound and outbound | Configure concurrency quotas separately for each line. |
| Signaling transport | UDP, TCP, or TLS | Select according to the carrier gateway's requirements. |
| Media encryption | None, SRTP, or DTLS-SRTP | Select according to the security level for the line. |
| Number format | E.164 or digits only | Do not include spaces or special characters. |
| Outbound caller ID | Unaltered caller ID using a carrier-registered number selected for each call | This is consistent with Japanese SIP practice. Multiple customer numbers can be registered and selected per call. |

A Register bridge is planned and is expected to become available during 2026.

## 3. Customer-Side Configuration

### 3.1 Daisybell Platform: Phone Numbers

Go to Tools → Phone Numbers. Admin and Daisybell Support users can view and edit this module; Sub-user accounts cannot see it. The former operations backend path, Tenant Management → Business Management → Line Management, has been retired and fully replaced by this module. The module supports Peer SIP Trunks (non-register), DTMF RFC 4733 (RFC 2833), G.711 and G.722, native Digest authentication, TLS signaling encryption, SRTP and DTLS-SRTP media encryption, and source allowlists for inbound calls.

#### 3.1.1 Configure Outbound Numbers

1. Go to Tools → Phone Numbers, open the Outbound Numbers tab, and select + Add New.
2. Enter the real outbound caller ID as digits only or in E.164 format.
3. Specify the Termination URI: the carrier's SIP gateway domain or IP address. The port is optional and defaults to 5060.
4. Select the transport (UDP, TCP, or TLS) and media encryption (None, SRTP, or DTLS-SRTP).
5. Enter SIP authentication credentials (Username and Password) if required.
6. Set the dedicated outbound-call and transfer concurrency quotas, then select Add Number.

| Parameter | Format | Description |
|-|-|-|
| Phone Number | Digits only or E.164 | The real outbound caller ID. |
| Termination URI / Address | Domain:port or IP:port | Carrier-provided SIP outbound gateway address (domain or IP; port optional), for example: `sip.example.com:5060` |
| Encryption | None, SRTP, or DTLS-SRTP | Media-stream encryption. Default: None. |
| Transport | UDP, TCP, or TLS | SIP signaling transport protocol. Default: UDP. |
| SIP Authentication | Username + Password | Optional. Enter this if the carrier requires registration or call authentication. The plaintext value cannot be viewed after saving. |
| Dedicated Outbound Concurrency | Integer, 0–1000 | Maximum number of regular outbound calls on this number. Default: 10. |
| Dedicated Transfer Concurrency | Integer, 0–1000 | Maximum number of human transfers on this number. Default: 0. Set this for every number that requires human transfer. |
| Show Main Caller ID For Transferred Calls | Toggle; off by default | When enabled, the original caller ID is passed through during transfer. Before enabling it, confirm that the carrier supports CLI pass-through; otherwise, the gateway may reject the transfer. |

#### 3.1.2 Configure Inbound Numbers

1. Open the Inbound Numbers tab and select + Add New.
2. Enter the inbound number as digits only or in E.164 format.
3. Configure the source allowlist for SIP INVITEs sent to the platform. Entries can be domains, IPv4 addresses, or CIDR ranges, with a maximum of 20 entries. If the other party's actual IP address is unknown, use 0.0.0.0/0 as a temporary wildcard and tighten the allowlist after integration testing.
4. Select the transport and media encryption.
5. Set the maximum inbound concurrency for the number. After validation succeeds, select Add Number.

| Parameter | Format | Description |
|-|-|-|
| Phone Number | Digits only or E.164 | The inbound number. |
| White List Address | Domain, IPv4, or CIDR | Allowlisted sources permitted to send INVITEs. Up to 20 entries are supported. Duplicate entries block submission. If the actual IP address is unknown, use 0.0.0.0/0 as a wildcard temporarily; see the guidance below. |
| Encryption | None, SRTP, or DTLS-SRTP | Media-encryption policy. |
| Transport | UDP, TCP, or TLS | SIP signaling transport protocol. |
| Total Call Concurrency | Integer, 1–1000 | Maximum inbound concurrency for the number. Default: 10. |

<callout emoji="💡">
**Allowlist guidance:** Prefer the carrier gateway's actual IP address, CIDR range, or domain. If the carrier's actual IP address is unknown, use 0.0.0.0/0 for inbound allowlisting during connectivity testing.**If the carrier gateway IP address is unknown, set the inbound allowlist to 0.0.0.0/0 (a wildcard that permits all sources) for connectivity testing.** This allows testing to proceed, but disables source validation and increases exposure to scans and spam. Once testing is stable, obtain the carrier gateway IP addresses and tighten the allowlist.
</callout>

#### 3.1.3 Line Statuses and Concurrency

| Status | Meaning | Available actions |
|-|-|-|
| Unused | Configured but not bound to an Agent. | Can be edited, disabled, or deleted. |
| In Use | Linked to an outbound task, inbound reception, or transfer strategy. | Cannot be deleted or disabled. Network settings can be edited only after confirmation. |
| Disabled | Manually stopped. The line cannot make or receive calls and is hidden from the Agent line list. | Re-enable the line to use it again. |

<callout emoji="💡">
Concurrency has three separate meanings: Outbound number total: dedicated outbound concurrency plus dedicated transfer concurrency. Platform concurrency quota: the flow-control quota configured in the UI. Actual line capacity: the channel capacity provided by the carrier gateway. If the platform quota exceeds the carrier's channel capacity, the carrier may reject calls, typically with SIP 503.
</callout>

### 3.2 Customer PBX

This path applies when the customer has a PBX that supports standard SIP. The connection can use a private line or VPN, or a direct public-IP connection with mutual IP allowlisting. It is usually the best option for latency and cost. See Integration Feasibility Criteria.

#### 3.2.1 Prerequisites and Number Routing

- Confirm that the PBX supports SIP Trunks and determine whether media bypass is supported.
- Confirm network reachability over a private line or VPN, or through reciprocal public-IP allowlists and permitted ports.
- Obtain the customer's PBX egress public IP address.
- Decide whether each DID should route to AI, a human agent, or outbound calling.

<callout emoji="💡">
 **For carrier-based connections (Paths 1 and 3), the carrier assigns the inbound DID; request or confirm it during provisioning. For a direct PBX connection (Path 2), the DID range is agreed between both parties and does not come from a carrier. For outbound calls in both cases, use caller IDs registered with the carrier.**DID assignment:
</callout>

#### 3.2.2 Generic IP-PBX Configuration

The field names vary by vendor. The following guidance applies to common FreePBX and Asterisk setups.

| Setting | Common value | Description |
|-|-|-|
| Trunk type | Peer (non-register), `type=peer` | Peer mode: set host to the other party's gateway IP; do not use a register string. |
| Server address / port | `host=<peer IP>`, default 5060/UDP | Each party configures the other party's address; use the port specified in the integration parameter sheet. |
| ACL allowlist | `permit`/`deny` or firewall rules | Allow only the peer SIP/RTP traffic. |
| Codec | `allow=ulaw` (G.711u) preferred | Matches the platform baseline and avoids unnecessary transcoding. |
| DTMF | `dtmfmode=rfc2833` | Required for extension transfers and secondary IVR dialing. |
| NAT | external address / localnet | Configure correctly when either side is behind NAT; otherwise one-way audio or no ringing may occur. |
| Inbound routing | Route by DID to a context | Route the DID to AI, an agent, or outbound handling. |
| Caller ID | Registered number only | Arbitrary caller IDs are not permitted; see the carrier requirements in Chapters 4 and 5. |

#### 3.2.3 Information to Exchange

| Direction | Content |
|-|-|
| Our team → customer | SIP gateway IP and port; transport protocol; codecs and DTMF requirements; our egress IP allowlist; DID list and routing requirements. |
| Customer → our team | PBX egress public IP; vendor and model; DID routing rules; test numbers and test window; agent-seat location. |

### 3.3 Human Transfer in Bridge Mode

The customer leg remains connected while the platform originates a second call to the agent. The platform bridges the two calls. During the human-assisted portion, audio continues to flow through our platform, allowing recording, transcription, and quality assurance.

| Agent seat location | Configuration guidance |
|-|-|
| PBX extension seat | Agent seat on the customer's PBX: Use the customer PBX path in Section 3.2. Set the transfer concurrency quota and permit the PBX connection. |
| Public service number seat | Agent seat on a public service number: Configure the transfer number and its concurrency. Carrier charges apply to the call through the PSTN. |
| PBX public DID routed to an extension | PBX public DID routed to an extension: Use DTMF to reach the extension. Confirm the IVR extension sequence and RFC 2833 support. |

<callout emoji="💡">
Transfer concurrency defaults to 0. Set it for every number used for human transfer.
</callout>

## 4. Carrier Integration in Japan

### 4.1 Number Types

| Type | Number format | Characteristics and use |
|-|-|-|
| 0AB-J geographic fixed-line number | 03 / 06 / 0X-XXXX-XXXX | Geographic fixed-line number with strong corporate recognition and high caller-ID trust. Eligibility or application through a carrier/agent may be required. |
| 050 IP phone number | 050-XXXX-XXXX | Low cost and quick provisioning; suitable for AI outbound calling and customer service. Some recipients may trust 050 numbers less than 0AB-J numbers. |
| Mobile number | 090 / 080 / 070-XXXX-XXXX | Generally not used as business caller ID. Confirm feasibility and compliance with the provider before choosing this option. |

### Common Access Methods

#### SIP Trunk Peer Connection (Mainstream)

- Both parties use static public IP addresses and configure reciprocal ACL allowlists.
- Limit the codec to PCMU and use RFC 2833/4733 for DTMF
- Use a designated, registered caller ID for outbound calls: register the customer's number with supporting evidence, then select it in the SIP message for each call.
- Confirm concurrency limits, CPS (calls per second), and the SLA.

#### 050 IP Phone Services

Many 050 IP phone services use Register mode. Confirm Peer support as a P0 item. If the provider supports Register only, use a relay or partner to convert the connection, or choose a Peer-capable provider.

### 4.3 Application and Provisioning

1. Define the number type, required concurrency, inbound/outbound mix, monthly traffic, and caller-ID display requirements.
2. Apply with the company name, representative, operator number, requested numbers, and channel count. Most applications require eligibility checks.
3. Provisioning may take from several days to several weeks. Confirm eligibility and the expected provisioning date.
4. Obtain the SIP parameters and assigned numbers. Configure allowlists and parameters as described in Section 4.2.
5. Test inbound and outbound calling, DTMF, caller ID, and concurrency.

| Information to request after provisioning | Details |
|-|-|
| Gateway information | SBC/SIP server address and port; transport protocol (UDP, TCP, or TLS). |
| Media parameters | Supported codecs, DTMF method, and media-encryption requirements. |
| Authentication | IP peer with ACL, or username and password. |
| Number information | Assigned numbers; caller-ID registration requirements and number format (domestic or E.164); number capacity and required documents. |
| Capacity and service commitments | Concurrency limit, CPS limit, SLA, and marketing-call policy. |
| Testing support | Test number, test window, and integration contact. |

### 4.4 Japan-Specific Notes

- Outbound caller IDs must be registered, consistent with anti-spoofing requirements.
- Compliance: follow Japan's Act on the Protection of Personal Information (APPI); notify callers about recording; retain and redact call data and logs according to the agreement.
- For 0AB-J numbers, register the location used for emergency calls such as 110 and 119. Update it when the location changes.

## 5. Carrier Integration in Korea

### 5.1 Number Types

| Type | Characteristics and use |
|-|-|
| 070 internet phone | A mainstream choice for AI and contact-center services in Korea. |
| Local geographic number | 02 (Seoul), 031, 032, 051, 053, and other regional prefixes. These support business recognition and can retain an existing number through number portability (번호이동). |
| Representative number (대표번호) | Corporate representative numbers such as 15XX, 16XX, and 18XX, associated with contact-center use. |
| Alternative number (대안번호) | 050-series corporate numbers used instead of a personal mobile number for caller ID. |

### 5.2 SIP Trunk Integration Paths

Direct SIP integration by a third-party AI provider is subject to caution and case-by-case approval. Consider two paths:

- Direct carrier Peer connection: IP-to-IP, Non-Register.
- Relay or partner through the carrier network: our platform side remains Peer, while the carrier-facing side uses Register. The platform endpoint must still meet the Peer requirement.

### 5.3 Korea-Specific Notes

- Emergency-calling address registration is required by law. Update the address when it changes; it affects location information for calls to 119 and 112.
- A customer's existing 02 or 070 number may be registered as outbound caller ID with subscription or contract evidence. Caller-ID spoofing or spam-related violations may lead to suspension or contract termination under applicable Korean rules.
- Number portability may be possible. Confirm feasibility, cost, and timing with the provider on a case-by-case basis.
- The platform supports multiple registered customer caller IDs and selects the applicable number per call in SIP.

## 6. Integration with External Calling Platforms

When a customer already uses a cloud contact-center platform, integration is primarily configured within that platform. The source describes Amazon Connect Flow + Lambda for dynamic DTMF and an external SIP Trunk (BYOC) for Genesys Cloud.

### 6.1 Amazon Connect: Dynamic DTMF Transfer Through Lambda

An inbound Amazon Connect contact flow can invoke Lambda to read the caller's number and create a DTMF sequence. The flow then uses a Transfer to phone number block to forward the call to the AI service or a downstream IVR. The destination identifies the caller from the DTMF digits.

```text
Inbound call → Amazon Connect Flow → Invoke Lambda (read CustomerEndpoint.Address
     → sanitize the number → return DtmfSequence)
   → Set contact attributes (External → User defined)
   → Transfer to phone number (send dynamic DTMF) → Destination
```

#### 6.1.1 Configuration

1. Create a Lambda function in the same AWS account and Region as the Connect instance (ap-northeast-1, Tokyo, in this example), and implement number sanitization by reading `Details.ContactData.CustomerEndpoint.Address`, removing non-digit characters, and returning `DtmfSequence` (Example: use a leading comma for a pause; if the original number begins with +, replace it with `*`, and end with `#`; the `+ → *` conversion is a downstream IVR convention; confirm it during integration testing.)
2. Attach the function to the target Connect instance: open Flows → AWS Lambda functions and add it. When both services are in the same account and Region, Connect automatically creates a Lambda resource policy for the connect.amazonaws.com principal.
3. Build the contact flow: add Set logging behavior (enable it during testing); add an Invoke AWS Lambda function block and select the function. Use synchronous JSON invocation, validate the response, and begin with a 3,000 ms timeout. In Set contact attributes, map External.DtmfSequence to User defined.DtmfSequence (attribute names are case-sensitive). In Transfer to phone number, enter the destination DID in E.164 format, configure Caller ID, and set Send DTMF to the dynamic attribute.
4. Connect the Success, Error, and Timeout branches; save and publish the flow; then confirm that the inbound number is associated with the published flow.

#### 6.1.2 Limits and Troubleshooting

| Symptom or limit | Guidance |
|-|-|
| DTMF sequence length | Maximum 50 characters. Each comma represents a 750 ms pause. |
| Lambda synchronous invocation | Maximum 8 seconds. Start with a 3,000 ms timeout and tune it using CloudWatch. |
| 403 AccessDeniedException | Check that the Lambda resource policy permits lambda:InvokeFunction for connect.amazonaws.com and that SourceArn and SourceAccount point to the intended instance. Confirm that the function is attached to the correct Connect instance and Region. |
| No Lambda logs | Check the Region, function ARN, and CloudWatch time range. |
| Empty contact attribute | Confirm the returned key is DtmfSequence and that the mapping is correct. |
| Transfer succeeds but no DTMF is received | First test a static sequence such as 123#, then test the dynamic value. Connect logs do not prove that the destination received the digits; verify at the destination. |

Recommended verification order: static transfer → fixed DTMF → attribute mapping → end-to-end test. Change one variable at a time. A detailed Amazon Connect Lambda DTMF configuration manual is attached in Section 6.1.

### 6.2 Genesys Cloud: BYOC External Trunk

Use an external BYOC trunk when the customer's carrier line connects to Genesys Cloud. SIP between Genesys and the carrier or our platform must follow the applicable standards.

#### Prerequisites

- A Genesys Cloud license and BYOC capability.
- Static public IP addresses and reciprocal allowlists; confirm SIP and RTP ports.
- Confirm compatibility with the platform baseline in Section 2.3: G.711, RFC 2833/4733, and UDP/TCP/TLS.

#### Configuration

1. Create a BYOC external trunk and configure the SBC.
2. Configure media and signaling according to Section 2.3.
3. Apply reciprocal IP allowlists and ACLs.
4. Route the DNIS to an Architect flow or the required destination.
5. Test inbound and outbound calls, DTMF, caller ID, and concurrency.

## 8. Troubleshooting Quick Reference

| Symptom | First checks |
|-|-|
| Inbound 403 Forbidden | Does the inbound allowlist include all carrier SBC/gateway IP addresses or CIDR ranges? |
| Outbound 503 Service Unavailable | Does the configured concurrency exceed carrier channel capacity? Is there a line time-window restriction? |
| Carrier supports Register only | Our platform does not support Register directly. Use a relay/partner to convert the connection or choose a Peer-capable provider. |
| One-way audio or no audio | Check NAT and RTP address configuration (external address, STUN, and firewall RTP port ranges). Confirm that SRTP settings match on both sides. |
| Caller ID is wrong or rejected | Confirm that the caller ID is registered with the carrier. Check the transfer pass-through toggle and carrier support for CLI pass-through. |
| IVR cannot be navigated or extension transfer fails | Check RFC 2833/4733 DTMF. Check the 50-character transfer DTMF limit and sequence format, including the + to \* convention. |
| Calls cannot be completed | Check transport protocol and ports, firewall rules, number format (E.164), and carrier provisioning status. |
| Number is missing from the Agent line selector | Check whether the line is Disabled and whether the inbound number matches the Agent call mode (Inbound). |
| An unused test number cannot be deleted | Check whether an Agent configuration depends on it as a fallback transfer number. Any such dependency makes the line In Use. |
