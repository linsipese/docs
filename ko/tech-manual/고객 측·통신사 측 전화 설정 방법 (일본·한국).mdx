현장 대응팀이 전화 회선 연결, 플랫폼 설정, 통신사 신청과 관련한 문의에 대응할 때 사용하는 표준 참고 매뉴얼입니다.

고객 측(Daisybell 플랫폼, 고객 PBX와 전화기), 통신사 측(일본·한국), Amazon Connect·Genesys 등 외부 콜 플랫폼의 연동 절차를 다룹니다.

## 문서의 목적 및 사용 방법

### 사용 방법

1. 연동 유형을 구분합니다. 고객 보유 회선을 직접 연결하는지, 당사 회선으로 외부 발신하는지, 고객 PBX에 연결하는지, Amazon Connect·Genesys를 경유하는지 확인합니다.
2. ‘발견 즉시 기록’ 원칙을 적용합니다. 새로운 연동 방식(새 회선 유형, PBX 브랜드, 플랫폼, 매개변수 조합)이 확정되면 해당 장에 내용을 추가하고 제9장 유지보수 기록에 날짜와 연동 대상을 남깁니다. 요금, 공급업체 비교, 신청 서류 세부 사항 등 통신사 영업 정보는 이 문서에 포함하지 않고 별도로 보관합니다.
3. 제7장 연동 정보 수집 목록에 따라 고객과 통신사에서 매개변수를 수집합니다. 모든 항목을 대조한 뒤 연동 테스트를 진행합니다.

### 유지보수 원칙

- ‘발견 즉시 기록’ 원칙: 새로운 연동 방식(새 통신사, PBX 브랜드, 플랫폼, 매개변수 조합)이 확정되면 해당 장의 ‘연동 이력’ 절에 내용을 추가하고 날짜와 연동 대상을 기록합니다.
- 요금, 정책, 화면 필드는 변경될 수 있습니다. 항상 최신 계약서, 통신사 요금표와 현재 콘솔을 기준으로 확인합니다.
- 고객 전화번호, 계정 비밀번호와 키 정보는 이 문서에 기록하지 않습니다. 해당 매개변수는 별도 자료로 전달합니다.

## 전체 아키텍처 및 플랫폼 기준

### 음성 경로 전체 아키텍처

당사 시스템은 자체 구축한 LiveKit(WebRTC 미디어 전달)과 livekit-sip(SIP/RTP 게이트웨이)로 음성 미디어를 처리합니다. 시스템 외부의 전화망(PSTN)에는 SIP Trunk로 연결합니다.

```Plaintext
Daisybell Voice Agent
        ↓
LiveKit(WebRTC 미디어 전달) + livekit-sip(SIP/RTP 게이트웨이)   ← 당사 플랫폼 측
        ↓
SIP Trunk(피어 방식/중계 경유)                              ← 연동 경계
        ↓
통신사 네트워크(일본/한국)                                ← 통신사 측
        ↓
PSTN → 고객 휴대전화/유선 전화/고객 PBX                        ← 고객 측
```

- **고객 측**: Daisybell 플랫폼에서 회선을 설정하고 고객 PBX, 전화기·소프트폰에 SIP를 설정합니다.
- **통신사 측**: 통신 회선과 SIP 중계를 신청·개통하고 연동 매개변수(서버 주소, 인증, 코덱, 번호 등록 등)를 제공합니다.
- **외부 플랫폼 측**: 고객이 Amazon Connect나 Genesys Cloud와 같은 콜 플랫폼을 사용하는 경우 해당 플랫폼에서 진행하는 설정 절차입니다.

### 두 가지 연동 방식: 피어(Peer) 및 등록(Register)

| 방식 | 원리 | 적용 대상 | 당사 지원 여부 |
|-|-|-|-|
| 피어(Peer / IP-to-IP, Non-Register) | 양측이 고정 공인 IP를 사용하고 ACL 허용 목록을 상호 등록합니다. 별도의 주기적 등록 없이 두 엔드포인트 사이에서 시그널링을 직접 전달합니다. | 통신사 직결, 클라우드 플랫폼 연동, 기업 전용 회선/VPN 환경 | **이 방식만 지원합니다.**(P0 필수 조건) |
| 등록(Register) | 단말이 계정과 비밀번호로 통신사 서버에 주기적으로 등록하고, 통신사는 등록 위치를 기준으로 통화를 라우팅합니다. | 일부 050 서비스, 고정 공인 IP가 없는 환경, 일반 고객에게 통신사가 기본 제공하는 방식 | 직접 지원하지 않습니다. 중계 회선이나 협력 업체를 통해 피어 방식으로 변환하거나(당사 구간은 피어 방식 유지, 통신사 구간은 등록 방식 사용) 피어 방식을 지원하는 공급업체를 선택해야 합니다. |



<callout emoji="💡">
공급업체 선정 시 다음 조건을 P0로 확인합니다. Daisybell SIP 엔드포인트는 피어 방식(Non-Register · IP-to-IP)만 지원하므로, 통신사 또는 협력 업체에 견적을 요청할 때 피어 연결 지원 여부를 가장 먼저 확인합니다.
</callout>

### SIP Trunk 기술 요구 사항(P0)

아래 항목은 Daisybell 개발팀이 확정한 기술 기준입니다. 양측 중 어느 한쪽이라도 기준을 충족하지 못하면 원칙적으로 연동할 수 없습니다.

| 항목 | 요구 사항 | 설명 |
|-|-|-|
| 연동 방식 | Non-Register · IP-to-IP 피어 방식 | 플랫폼에서 지원하는 유일한 연동 방식 |
| 코덱 | G.711u(PCMU) | G.722도 지원합니다. 협상 과정의 혼선을 줄이려면 연동 시 ulaw로 제한하는 것을 권장합니다 |
| DTMF | RFC 4733 | RFC 2833은 동일 방식의 이전 규격이며 호환됩니다. 통신사가 RFC 2833을 제공해도 됩니다 |
| 방향 | 인바운드 + 아웃바운드 | 회선별로 동시 통화 한도를 설정합니다 |
| 시그널링 전송 | UDP / TCP / TLS | 통신사 게이트웨이 규격에 맞춰 선택합니다 |
| 미디어 암호화 | None / SRTP / DTLS-SRTP | 회선의 보안 등급에 따라 선택합니다 |
| 번호 형식 | E.164 또는 숫자만 입력 | 공백과 특수 문자는 입력할 수 없습니다 |
| 아웃바운드 발신 번호 | 통화별로 통신사 등록 번호를 지정하며 임의로 변경하지 않습니다 | 일본 SIP 환경과 동일하게 여러 고객 번호를 등록하고 통화별로 선택할 수 있습니다 |

\* Register 브리지는 개발 계획에 있으며 2026년 중 출시 예정입니다.

## 고객 측 설정

### Daisybell 플랫폼 측(Phone Numbers 모듈)

경로: Tools → Phone Numbers. Admin과 Daisybell Support는 조회·편집 권한을 가지며 Sub-user에게는 표시되지 않습니다. 기존 운영 콘솔의 [테넌트 관리] → [업무 관리] → [회선 관리] 모듈은 종료되었고 Phone Numbers가 해당 기능을 대체합니다. 피어 SIP Trunk(비등록), DTMF RFC 4733(RFC 2833), G.711/G.722, 기본 Digest 인증, TLS 시그널링 암호화, SRTP/DTLS-SRTP 미디어 암호화를 지원합니다. 인바운드에서는 발신지 허용 목록을 설정할 수 있습니다.

#### 아웃바운드 번호(Outbound Numbers) 설정

1. Tools → Phone Numbers로 이동해 Outbound Numbers 탭을 엽니다. + Add New를 클릭합니다.
2. 번호 입력: 실제 발신 번호를 숫자만 입력하거나 E.164 형식으로 입력합니다.
3. 발신 게이트웨이(Termination URI) 지정: 통신사 SIP 게이트웨이의 도메인 또는 IP를 입력합니다. 포트는 생략할 수 있으며 기본값은 5060입니다.
4. 전송 방식(UDP/TCP/TLS)과 미디어 암호화(None/SRTP/DTLS-SRTP)를 지정합니다.
5. 필요한 경우 SIP 인증 정보(Username / Password)를 입력합니다.
6. 동시 통화 한도를 설정합니다. 발신 전용·전환 전용 동시 통화 수를 지정한 뒤 Add Number를 클릭합니다.

| 매개변수 | 형식 | 설명 |
|-|-|-|
| Phone number | 숫자만 입력 또는 E.164 | 실제 발신 번호 |
| Termination URI / Address | 도메인:포트 또는 IP:포트 | 통신사가 제공하는 SIP 발신 게이트웨이 주소입니다. 포트는 생략할 수 있습니다. 예: `sip.example.com:5060` |
| Encryption | None / SRTP / DTLS-SRTP | 미디어 스트림 암호화 설정입니다. 기본값은 None입니다. |
| Transport | UDP / TCP / TLS | SIP 시그널링 전송 프로토콜입니다. 기본값은 UDP입니다. |
| SIP Authentication | Username + Password | 선택 사항입니다. 통신사가 등록 또는 호출 인증을 요구할 때 입력합니다. 저장 후에는 비밀번호를 평문으로 확인할 수 없습니다. |
| Dedicated Outbound Concurrency | 정수 0–1000 | 해당 번호의 일반 아웃바운드 최대 동시 통화 수입니다. 기본값은 10입니다. |
| Dedicated Transfer Concurrency | 정수 0–1000 | 해당 번호의 상담원 전환 최대 동시 통화 수입니다. 기본값은 0입니다. 상담원 전환이 필요한 번호에는 값을 설정해야 합니다. |
| Show Main Caller ID For Transferred Calls | 스위치, 기본값 꺼짐 | 활성화하면 통화 전환 중에도 최초 발신 번호를 전달합니다. 설정 전에 통신사가 CLI 전달을 지원하는지 확인합니다. 미지원 시 게이트웨이가 전환을 거부할 수 있습니다. |

#### 인바운드 번호(Inbound Numbers) 설정

1. Inbound Numbers 탭을 열고 + Add New를 클릭합니다.
2. 인바운드 번호를 숫자만 입력하거나 E.164 형식으로 입력합니다.
3. 허용 목록을 설정합니다. 플랫폼으로 SIP INVITE를 보낼 수 있는 발신지의 도메인, IPv4 주소 또는 CIDR 네트워크를 최대 20개까지 등록할 수 있습니다. 상대방의 실제 IP를 모르는 경우 우선 0.0.0.0/0 와일드카드로 전체 발신지를 허용한 뒤, 연동 테스트 후 허용 범위를 좁힙니다(아래 기준 참조).
4. 전송 방식과 미디어 암호화를 선택합니다.
5. 해당 번호의 최대 인바운드 동시 통화 수를 설정합니다. 검증을 통과한 뒤 Add Number를 클릭합니다.

| 매개변수 | 형식 | 설명 |
|-|-|-|
| 전화번호 | 숫자만 입력 또는 E.164 | 인바운드 번호 |
| White List Address | 도메인 / IPv4 / CIDR | INVITE를 보낼 수 있는 발신지 허용 목록입니다. 최대 20개까지 등록할 수 있습니다. 중복 항목이 있으면 등록할 수 없습니다. 상대방의 실제 IP를 모르는 경우 0.0.0.0/0 와일드카드를 입력할 수 있습니다(아래 기준 참조) |
| Encryption | None / SRTP / DTLS-SRTP | 미디어 암호화 정책 |
| Transport | UDP / TCP / TLS | 인바운드 시그널링을 수신할 프로토콜 |
| Total Call Concurrency | 정수 1–1000 | 최대 동시 통화 연결 수입니다. 기본값은 10입니다 |



<callout emoji="💡">
**허용 목록 설정 기준: 통신사 게이트웨이 IP/CIDR 또는 도메인을 우선 등록합니다. 상대방의 실제 IP를 모르는 경우 인바운드 허용 목록에 0.0.0.0/0 와일드카드를 설정할 수 있습니다. 이 상태에서는 모든 발신지를 허용하므로 연동 테스트는 가능하지만 발신지 검증이 이루어지지 않아 스캔이나 불필요한 접속에 노출될 수 있습니다. 테스트가 안정화되면 통신사에서 게이트웨이 IP를 받아 허용 범위를 즉시 좁힙니다.**
</callout>

#### 회선 상태 및 동시 통화 한도

| 상태 | 정의 | 제한 |
|-|-|-|
| Unused(미사용) | 설정은 완료되었지만 Agent에 연결되지 않은 상태입니다. | 편집·비활성화·삭제할 수 있습니다 |
| In Use(사용 중) | 아웃바운드 작업, 인바운드 응대 또는 전환 정책에 연결된 상태입니다. | 삭제하거나 비활성화할 수 없습니다. 네트워크 매개변수를 수정할 때는 재확인이 필요합니다 |
| Disabled(비활성화됨) | 수동으로 비활성화되어 통화를 처리하지 않는 상태입니다. | 모든 Agent 회선 목록에서 숨겨집니다 |

<callout emoji="💡">
동시 통화 수는 세 가지 기준으로 구분합니다. 발신 번호의 전체 동시 통화 수는 발신 전용 동시 통화 수와 전환 전용 동시 통화 수를 합산한 값입니다. 플랫폼 화면에서 설정하는 값은 플랫폼 측 트래픽 제어 할당량이며, 회선의 실제 동시 통화 용량은 통신사 게이트웨이 용량에 따라 결정됩니다. 플랫폼 할당량을 높게 설정해도 통신사 채널 용량을 초과하면 통신사에서 호출을 거부할 수 있습니다(일반적으로 SIP 503 Service Unavailable).
</callout>

### 고객 PBX 연동(경로 2)

적용 대상: 고객이 표준 SIP를 지원하는 PBX를 보유하고 기업 전용 회선/VPN 또는 공인망 IP 허용 목록으로 직접 연동할 수 있는 경우입니다. 일반적으로 지연 시간과 비용 측면에서 가장 유리한 경로입니다. 자세한 내용은 ‘연동 가능성 판단 기준’을 참조합니다.

#### 사전 조건

- 고객 PBX가 SIP Trunk 연결(중계/peer 설정)을 지원해야 하며, 미디어 우회(media bypass) 지원 여부도 확인해야 합니다.
- 네트워크가 연결되어야 합니다. 전용 회선/VPN을 사용하거나 공인망에서 양방향으로 허용된 IP와 포트를 사용합니다.
- 고객은 상호 허용 목록 설정에 필요한 PBX 출구 공인 IP를 제공해야 합니다.
- DID 라우팅 규칙을 정합니다. 어떤 번호를 AI로 보낼지, 상담원에게 연결할지, 외부로 발신할지 구분합니다.

<callout emoji="💡">
**DID 번호 출처: 통신사 회선(경로 1/3)을 거치는 인바운드 통화의 DID는 통신사가 할당합니다. 회선 개통 시 번호 자원을 신청하고 확인합니다. PBX 직접 연결(경로 2)에서는 통신사 개입 없이 양측이 DID 번호 대역을 협의합니다. 두 방식 모두 아웃바운드 발신 표시 번호는 통신사 등록 번호를 사용해야 합니다.**
</callout>

#### 일반 IPPBX 중계 매개변수(FreePBX / Asterisk 등)

브랜드마다 필드명은 다르지만 매개변수의 의미는 동일합니다. 아래 표는 고객 IT 담당자 또는 채널 엔지니어와 설정 기준을 맞출 때 참고할 수 있는 Asterisk 계열의 일반적인 표기입니다.

| 매개변수 | 일반적인 값 | 설명 |
|-|-|-|
| 중계 유형 | Peer(등록하지 않음),`type=peer` | 피어 방식에서는 host에 상대방 게이트웨이 IP를 입력합니다. register 문자열은 입력하지 않습니다 |
| 서버 주소/포트 | `host=<상대방 IP>`, 기본값 5060/UDP | 양측에서 상대방 주소를 각각 설정합니다. 포트는 연동 매개변수 문서를 따릅니다 |
| 허용 목록 ACL | `permit`/`deny` 또는 방화벽 규칙 | 상대 IP의 SIP/RTP 트래픽만 허용합니다 |
| 코덱 | `allow=ulaw`(G.711u) 우선 | 불필요한 코덱 변환을 피하도록 당사 기술 기준에 맞춰 설정합니다 |
| DTMF | `dtmfmode=rfc2833` | 내선 전환과 IVR 후속 입력에 필요합니다 |
| NAT | external address / localnet | 양측 중 한 곳이라도 NAT 환경이면 정확히 설정해야 합니다. 미설정 시 단방향 음성 또는 무응답 문제가 발생할 수 있습니다 |
| 인바운드 라우팅 | DID에 따라 context를 매칭합니다 | DID를 AI 회선, 상담원 또는 외부 발신 경로로 분기합니다 |
| 발신 표시 번호 | 등록된 번호 | 발신 번호를 임의로 설정할 수 없습니다. 통신사 등록 요건은 제4장과 제5장을 참조합니다 |

#### 양측 간 교환 정보

| 방향 | 내용 |
|-|-|
| 당사 → 고객 | SIP 게이트웨이 IP와 포트, 전송 프로토콜, 코덱·DTMF 요구 사항, 허용 목록에 등록할 당사 출구 IP, DID 목록과 라우팅 요구 사항 |
| 고객 → 당사 | PBX 출구 공인 IP, 제조사·모델, DID 라우팅 규칙, 테스트 번호와 테스트 일정, 상담원 위치 |

### 상담원 전환(브리지 방식)

AI 통화 중 상담원에게 전환할 때는 브리지 방식을 적용합니다. 고객과의 기존 통화는 유지하고 상담원에게 별도 통화를 연결한 뒤 당사에서 두 통화를 브리지합니다. 상담원 통화 음성도 모두 당사 시스템을 거치므로 녹음·텍스트 변환·품질 검수가 가능합니다.

| 상담원 위치 | 설정 요점 |
|-|-|
| PBX 내선 상담원 | 경로 2 연동에 추가 설정이 필요합니다. 고객 PBX를 통해 상담원 내선으로 연결하고 전용 전환 동시 통화 수를 설정합니다. PBX가 전환 통화를 허용하는지도 확인합니다 |
| 공중망 고객센터 번호 | PSTN 번호로 전환하는 경우 플랫폼에 전용 전환 번호와 동시 통화 수를 설정합니다. 통화 요금은 통신사 요금표를 따릅니다 |
| PBX 공중망 번호를 통한 내선 연결 | PBX 공중망 DID와 DTMF로 내선에 연결하는 경우 고객 IVR의 내선 번호와 DTMF 방식(RFC 2833)을 확인합니다 |

<callout emoji="💡">
전환 동시 통화 수의 기본값은 0입니다. 상담원 전환이 필요한 번호는 발신·수신 설정에서 Dedicated Transfer Concurrency를 지정해야 합니다. 값을 설정하지 않으면 전환을 시작할 수 없습니다.
</callout>

## 통신사 측(일본)

### 번호 및 회선 유형

| 유형 | 번호 형식 | 특징 및 적용 대상 |
|-|-|-|
| 0AB-J 고정전화 번호 | 03 / 06 / 0X-XXXX-XXXX | 지역번호가 포함된 고정전화 번호입니다. 기업 식별력과 발신 표시 신뢰도가 높습니다. 회선 개통에는 사업 자격이 필요할 수 있으며 통신사 또는 대리점을 통해 신청합니다 |
| 050 IP 전화 | 050-XXXX-XXXX | 비용이 낮고 개통이 빠른 IP 전화번호로, AI 발신과 고객 응대에 적합합니다. 일부 수신자는 050 번호를 0AB-J보다 덜 신뢰할 수 있습니다 |
| 휴대전화 번호 | 090 / 080 / 070-XXXX-XXXX | 일반적으로 업무용 발신 표시 번호로 사용하지 않습니다. 사용 전 통신사에 이용 가능 여부와 규정 준수 여부를 확인합니다 |

### 일반적인 연결 방식

#### SIP Trunk 피어 연결(주요 방식)

- 양측이 고정 공인 IP를 사용하고 ACL 허용 목록을 서로 등록합니다.
- 코덱은 PCMU로 제한하며 DTMF는 RFC 2833/4733을 사용합니다.
- 아웃바운드 발신 번호는 ‘등록된 번호 지정’ 방식으로 사용합니다. 고객 번호를 증빙 자료와 함께 등록한 뒤 SIP 메시지에서 등록 번호를 선택합니다.
- 동시 통화 한도, CPS(초당 호출 수) 제한과 SLA를 확인합니다.

#### 050 IP 전화 서비스

일반적인 050 서비스는 계정과 비밀번호를 사용하는 등록 방식을 제공합니다. 공급업체 선정 시 피어 연결 지원 여부를 P0 항목으로 먼저 확인합니다. 등록 방식만 제공하는 서비스는 게이트웨이·중계 회선을 통해 피어 방식으로 변환하거나 피어 연결을 지원하는 업체를 선택해야 합니다.

### 신청 및 개통 절차와 서류

1. 요구 사항 확인: 번호 유형(0AB-J/050), 동시 통화 회선 수, 인바운드·아웃바운드 비율, 월간 통화량과 발신 표시 요구 사항을 확인합니다.
2. 신청서 제출: 회사 정보, 대표자 정보, 사업자 정보(번호), 신청 번호와 채널 수를 제출합니다. 대부분의 서비스는 자격 심사를 진행합니다.
3. 개통: 서비스 제공업체에 따라 며칠에서 몇 주가 소요될 수 있습니다. 개통 과정에서 심사 결과와 개통 일정을 확인합니다.
4. 통신사의 개통 자료(SIP 매개변수와 번호 정보)를 받은 뒤 제4.2절에 따라 양측의 허용 목록과 매개변수를 설정합니다.
5. 통화 테스트: 인바운드, 아웃바운드, DTMF, 발신 표시와 동시 통화를 항목별로 검증한 뒤 서비스를 개시합니다.

| 개통 후 통신사에 요청할 정보 | 내용 |
|-|-|
| 게이트웨이 정보 | SBC/SIP 서버 주소와 포트, 전송 프로토콜(UDP/TCP/TLS) |
| 미디어 매개변수 | 코덱, DTMF 방식, 미디어 암호화 필요 여부 |
| 인증 방식 | IP 피어 연결 + ACL 또는 계정·비밀번호 |
| 번호 정보 | 할당 번호 목록, 발신 번호 등록 요건과 형식(국내 형식/E.164), 등록 가능 번호 수와 필요 서류 |
| 용량 및 서비스 보장 | 동시 통화 상한, CPS 제한, SLA와 마케팅 전화 정책 |
| 테스트 지원 | 테스트 번호, 테스트 일정과 연동 담당자 |

### 일본 유의 사항

- 발신 번호 등록 제도: 발신번호 위·변조 방지 규정에 따라 아웃바운드 발신 번호는 통신사 등록 번호를 사용해야 하며 임의로 설정할 수 없습니다.
- 규정 준수: 개인정보는 개인정보 보호법(APPI)에 따라 처리합니다. 통화 녹음은 사전에 안내하고 통화 데이터와 로그는 합의된 범위에서 보관·비식별 처리합니다.
- 긴급 신고: 0AB-J 회선은 설치 주소를 등록해야 합니다(110/119 위치 확인). 주소를 이전하면 등록 정보도 갱신합니다.

### 연결 경로

한국 통신사는 제3자 AI 업체와의 직접 SIP 연결을 신중하게 검토하며 개별 승인을 요구하는 경우가 많습니다. 현재 검토 가능한 경로는 두 가지입니다.

- 통신사 직결 피어 회선 상품(IP-to-IP Peer, Non-Register)을 사용합니다.
- 통신사 네트워크의 중계 회선 또는 협력 서비스 업체를 이용합니다. 당사 구간은 피어(Non-Register) 방식으로 유지하고, 통신사 구간은 협력 업체가 등록 방식으로 연결합니다. 따라서 플랫폼 엔드포인트는 피어 기술 기준을 충족합니다.

### 한국 유의 사항

- 긴급통신 주소 신고는 법적 의무입니다. 설치 주소가 변경되면 신고해야 하며, 해당 정보는 119/112 위치 확인에 사용됩니다.
- 발신 번호 등록 제도: 고객이 기존에 사용하던 02/070 번호는 가입 증명서나 계약서로 소유권을 증빙한 뒤 아웃바운드 발신 번호로 등록할 수 있습니다. 스팸 전화 또는 발신번호 위·변조가 확인되면 서비스가 정지되거나 계약이 해지될 수 있습니다(한국 공통 규정).
- 번호 이동(번호이동): 고객의 기존 번호를 유지할 수 있습니다. 이용 가능 여부와 비용·처리 기간은 회선 제공업체에 확인합니다.
- 통화별로 등록 발신 번호를 지정합니다. 일본과 동일하게 여러 고객 번호를 한 환경에 등록하고 SIP 메시지에서 통화별로 선택할 수 있습니다.

## 외부 콜 플랫폼 연동(Amazon Connect / Genesys)

고객이 이미 클라우드 콜센터 플랫폼을 사용한다면 연동 작업의 중심은 통신사 설정에서 플랫폼(외부 시스템) 설정으로 이동합니다. 대표적인 방식은 Amazon Connect의 Flow + Lambda 기반 동적 DTMF 전환과 Genesys Cloud의 외부 SIP Trunk(BYOC) 연결입니다.

### Amazon Connect(Lambda 동적 DTMF 전환)

시나리오: 수신 전화가 Amazon Connect의 음성 Contact Flow로 들어오면 Lambda가 발신 번호를 조회해 DTMF 시퀀스를 생성합니다. Transfer to phone number 블록은 AI 회선이나 후속 IVR 등 대상 번호로 통화를 전환하고, 후속 시스템은 DTMF로 고객 번호를 식별합니다.

```text
수신 전화 → Amazon Connect Flow → Invoke Lambda(CustomerEndpoint.Address 읽기
      → 번호 정리 → DtmfSequence 반환)
    → Set contact attributes(External → User defined)
    → Transfer to phone number(동적 DTMF 전송) → 대상 번호
```

#### 플랫폼 설정 절차(AWS 콘솔)

1. Lambda 콘솔에서 함수를 생성합니다(Connect 인스턴스와 함수는 동일한 계정·리전에 있어야 합니다. 예: 도쿄 ap-northeast-1). 번호 정리 코드를 배포합니다. 코드에서 `Details.ContactData.CustomerEndpoint.Address`를 읽고 숫자가 아닌 문자를 제거한 뒤 `DtmfSequence`를 반환합니다(예시 규칙: 첫 번째 쉼표는 대기로 처리하고, 원래 번호에 +가 있으면 `*`로 변환하며 끝에 `#`를 추가합니다. `+ → *`는 후속 IVR과의 약속이므로 연동 테스트에서 확인합니다.)
2. Connect 콘솔에서 대상 인스턴스 → Flows → AWS Lambda functions로 이동해 함수를 추가합니다. 계정과 리전이 동일하면 Lambda 리소스 정책(Principal: connect.amazonaws.com)이 자동으로 생성됩니다.
3. Flow를 다음 순서로 구성합니다. Set logging behavior(테스트 중 Enable) → AWS Lambda function 블록(Invoke Lambda / Synchronous / JSON 검증, Timeout은 우선 3000ms로 설정) → Set contact attributes(External.DtmfSequence를 User defined.DtmfSequence에 복사하고 키 대소문자를 동일하게 유지) → Transfer to phone number(대상 DID를 E.164로 설정하고 Caller ID를 지정한 뒤 Send DTMF에서 동적 속성을 참조).
4. Success / Error / Timeout 분기를 각각 연결한 뒤 저장하고 Publish합니다. 인바운드 번호가 해당 Flow에 연결되어 있는지 확인합니다.

#### 주요 제한 사항 및 문제 해결

| 항목 | 설명 |
|-|-|
| DTMF 길이 | Transfer to phone number는 DTMF 문자를 최대 50개까지 전송할 수 있습니다. 쉼표 하나는 750ms 대기로 처리됩니다 |
| 동기 호출 시간 초과 | Lambda 동기 호출의 최대 시간 제한은 8초입니다. Timeout은 우선 3000ms로 설정하고 CloudWatch 실행 시간을 확인해 조정합니다 |
| 403 AccessDeniedException | Lambda 리소스 정책에서 connect.amazonaws.com에 lambda:InvokeFunction 권한을 허용하는지 확인합니다. SourceArn / SourceAccount가 올바른 인스턴스를 가리키는지, 함수가 올바른 인스턴스와 리전에 추가되었는지도 확인합니다. |
| Lambda 실행 기록이 없음 | Connect 리전과 Flow에 설정된 함수 ARN, CloudWatch 리전과 조회 시간 범위를 확인합니다 |
| 속성이 비어 있음 | 반환 키가 DtmfSequence인지, External에서 User defined로의 매핑이 올바른지 확인합니다. |
| 전환은 성공했지만 DTMF가 수신되지 않음 | 먼저 123#과 같은 짧은 고정 시퀀스로 채널을 검증한 뒤 동적 속성 참조를 확인합니다. Connect 로그만으로 후속 시스템의 실제 키 입력 수신 여부를 알 수 없으므로 대상 측에서도 확인합니다 |

검증은 정적 전환(고정 DID, Lambda 미사용) → 고정 DTMF → 동적 매핑 → 번호를 사용한 엔드투엔드 검증 순서로 진행합니다. 한 번에 하나의 변수만 변경합니다. Lambda 코드, 권한 정책 세부 사항, CloudWatch Flow Logs 사용법과 출시 점검표가 포함된 전체 매뉴얼을 참조합니다:

### Genesys Cloud(외부 SIP Trunk 연결)

Genesys는 외부 SIP Trunk 연결을 사용합니다. 고객 통신사 회선을 BYOC(Bring Your Own Carrier) 클라우드 중계로 Genesys Cloud에 연결하고, Genesys와 통신사 또는 당사 플랫폼은 표준 SIP로 연동합니다.

#### 사전 조건

- Genesys Cloud 라이선스와 BYOC 권한이 필요합니다(BYOC는 Genesys에 신청해 활성화합니다).
- 연동 양측에 고정 공인 IP가 있어야 합니다. 허용 목록을 서로 설정하고 SIP/RTP 포트를 개방합니다.
- 회선 미디어 매개변수가 플랫폼 기준(G.711, RFC 2833/4733, UDP/TCP/TLS)과 일치해야 합니다.

#### 설정 절차

1. Genesys Cloud 관리 센터에서 External Trunk(BYOC)를 생성하고 통신사 또는 연동 측 SBC 주소·포트·프로토콜을 입력합니다.
2. 시그널링과 미디어 매개변수(코덱, DTMF, 전송, 암호화)를 제2.3절의 플랫폼 기술 기준에 맞춰 설정합니다.
3. 양방향 허용 목록/ACL을 설정하고 네트워크 연결 상태를 확인합니다.
4. 번호 라우팅을 설정합니다. DNIS를 해당 Architect Flow 또는 전환 대상에 매핑합니다.
5. 인바운드, 아웃바운드, DTMF, 발신 표시와 동시 통화를 항목별로 연동 테스트한 뒤 서비스를 개시합니다.

#### 비용 참고

| 항목 | 산정 기준 |
|-|-|
| BYOC 클라우드 중계(외부 SIP Trunk) | 고객 보유 통신사 회선을 Genesys Cloud에 연결하면 좌석당 월 5,000분이 포함됩니다. 초과 요금은 분당 약 0.0012달러입니다(2026년 9월 자료이며 최신 요금표를 확인합니다) |

## 자주 발생하는 문제 빠른 점검

| 증상 | 우선 확인 사항 |
|-|-|
| 인바운드 403 Forbidden | 인바운드 허용 목록에 통신사 SBC 또는 게이트웨이의 IP/CIDR이 모두 등록되어 있는지 확인합니다 |
| 아웃바운드 503 Service Unavailable | 플랫폼의 동시 통화 한도가 통신사 채널 용량을 초과하지 않는지, 회선에 이용 시간 제한이 있는지 확인합니다 |
| 통신사가 등록 방식만 제공함 | 당사 플랫폼은 등록 방식을 지원하지 않습니다. 중계 회선이나 협력 업체를 통해 피어 방식으로 변환하거나 피어 연결을 지원하는 공급업체를 선택합니다 |
| 한쪽 음성만 들리거나 오디오가 없음 | NAT 및 RTP 주소(external address, STUN, 방화벽의 RTP 포트 범위), 양측의 SRTP 설정이 일치하는지 확인합니다 |
| 발신 표시 번호가 잘못되었거나 거부됨 | 발신 번호가 통신사에 등록되어 있는지, 통화 전환 시 번호 전달 스위치와 통신사의 CLI 전달 지원 여부를 확인합니다 |
| IVR 메뉴에 진입할 수 없거나 내선 전환에 실패함 | DTMF 방식이 RFC 2833/4733인지 확인합니다. 전환 DTMF 50자 제한과 시퀀스 형식(+ → \* 규칙)도 확인합니다 |
| 통화가 전혀 연결되지 않음 | 전송 프로토콜과 포트, 방화벽, 번호 형식(E.164), 통신사 개통 상태를 순서대로 확인합니다 |
| Agent 회선 드롭다운에 번호가 표시되지 않음 | 회선이 Disabled 상태인지, 인바운드 번호와 Agent 통화 모드(Inbound)가 일치하는지 확인합니다 |
| 미사용 테스트 번호를 삭제할 수 없음 | 해당 번호가 Agent의 예비 전환 번호로 지정되어 있는지 확인합니다. 의존성이 남아 있으면 In Use 상태로 처리됩니다 |
